# 절차 세부

`SKILL.md` 흐름 1~6의 세부 규칙이다. 순서와 번호는 `SKILL.md`와 같다.

## 1. 보고 채널

시작할 때 한 번만 묻는다. 작업 중에는 채널과 3절의 수락 외에는 질문하지 않는다.

| 채널 | 값 | 전달 방법 |
|---|---|---|
| 표준 출력(기본) | `stdout` | 대화 마지막 메시지에 보고서를 그대로 출력 |
| GitHub PR body | `github-pr` | 현재 브랜치 PR body에 `## 사람이 판단할 것` 섹션을 추가·갱신. PR이 없으면 stdout에도 남김 |
| GitHub issue | `github-issue` | 지정한 issue에 코멘트로 추가. 번호가 없으면 새 issue 생성 |
| 파일 | `file:<경로>` | 지정 경로에 Markdown으로 저장 |

질문 예시:

```text
보고 채널을 정해주세요. stdout(기본) / github-pr / github-issue(#번호) / file:<경로>
답이 없으면 stdout으로 진행합니다.
```

- 답이 없거나 비대화형이면 `stdout`으로 진행하고 보고 첫 줄에 `채널: stdout(기본값)`을 적는다.
- GitHub 채널인데 `gh`나 GitHub MCP가 없으면 `stdout`으로 내려가고 그 사실을 보고 첫 줄에 적는다.

## 2. 범위·계약·기준선

변경 전에 아래를 확정하고 채팅에 짧게 남긴다.

- 범위: 파일·디렉터리 목록. 사용자가 말한 범위를 넘지 않는다.
- 계약: 사용자에게 보여야 할 동작, 항상 지켜야 할 조건(불변식·에러 처리·성능 상한), 누가 어떤 데이터를 읽고 바꾸는지. 문서라면 전달하려는 사실과 절차.
- 작업 트리: 커밋되지 않은 변경이 있으면 건드리지 않고 사람 항목으로 적는다. stash·reset 하지 않는다.

검증 매트릭스는 [`verification-catalog.md`](verification-catalog.md)의 순서로 찾는다. 저장소가 정한 것 → 표준 도구 → 없음.

| 대상 | 검증 | 명령 | 기준선 |
|---|---|---|---|
| `src/order/` | 단위 테스트 | `pytest tests/order -q` | 통과 |
| `src/order/` | 타입 검사 | `mypy src/order` | 실패 2건(기존) |
| `docs/*.md` | 문서 검사 | `markdownlint docs` | 통과 |
| `deploy/*.yaml` | 없음 | - | - |

- 변경 전에 전부 한 번 실행해 기준선을 얻는다. 기준선 실패는 사람 항목 `기준선 실패`로 적고 고치지 않는다.
- `없음`인 대상을 고치면 그 변경은 전부 사람 항목이다. 최소 검증 하나(파싱 테스트 등) 추가를 제안할 수 있고, 추가한 검증도 사람 항목이다.
- 검증이 오래 걸리면 단위마다 대상 범위만 돌리고 마지막에 전체를 한 번 돌린다.

## 3. 제안과 수락

고치기 전에 무엇을 어떤 근거로 바꿀지 목록으로 보인다. 근거는 코드 위치, 참조 수, 계약과의 관계, 검증 유무 중 하나 이상이다.

```markdown
## 제안

범위: `src/order/`, `docs/order.md` · 계약: 주문 생성 API 응답 형식 유지, 재시도 5회

| # | 대상 | 조치 | 내용 | 근거 |
|---|---|---|---|---|
| 1 | `src/order/service.py:40-88` | 수정 | 중복 검증 로직 3곳을 함수 하나로 | 동일 코드 3곳, `tests/order` 커버 |
| 2 | `docs/order-legacy.md` | 삭제 | 문서 전체 | 참조 0건, 설명하는 명령이 코드에 없음 |
| 3 | `src/order/utils.py:12` | 삭제 | 미사용 함수 `fmt_legacy` | 호출 0건(`grep -rn fmt_legacy`) |
| 4 | `tests/order/test_parse.py` | 생성 | 파싱 테스트 | `parse.py` 검증 수단 없음 |

수락: 전체 / 번호 지정(예: 1,3,4) / 거절
```

삭제를 제안하는 기준:

- 참조가 없다: 호출·import·링크 0건
- 계약에 기여하지 않는다: 범위 안에 있지만 유지할 동작·조건과 무관
- 코드와 어긋난다: 문서·주석·설정이 현재 코드와 다른 사실을 말함
- 중복이다: 같은 목적의 코드·문서가 다른 곳에 있음

규칙:

- 수락 전에는 어떤 파일도 고치지 않는다.
- 부분 수락이면 수락된 번호만 진행한다. 거절·무응답이면 제안서를 보고서로 채널에 전달하고 끝낸다.
- 진행 중 제안에 없던 변경이 필요해지면 그 단위는 진행하지 않고 사람 항목 `가정`으로 적는다.

## 4. 변경·검증 반복

수락된 단위 하나마다 반복한다. 단위는 목적이 하나인 변경이다(이름 바꾸기 하나, 함수 추출 하나, 문서 섹션 하나).

1. 변경한다.
2. 그 대상의 검증을 돌린다.
3. 실패하면 내 변경의 원인을 고치고 다시 돌린다.
4. 3번 시도해도 실패하면 되돌리고 사람 항목 `되돌림`으로 적는다. 실패 출력의 핵심 줄을 남긴다.

아래는 통과로 인정하지 않고 사람 항목 `검증 우회`로 적는다.

- 테스트·기대값·스냅샷·golden 파일을 바꾼 것
- 린트 규칙을 끄거나 `ignore` 주석을 붙인 것
- 검증 명령의 범위를 줄인 것

사용자가 커밋을 요청했으면 단위마다 커밋한다. 요청이 없으면 커밋하지 않는다.

## 5. 사람 항목 판정

| 판정 | 예 |
|---|---|
| 자동 검증 없음 | 검증 수단이 없는 대상의 변경 |
| 동작·인터페이스 변경 | 공개 함수 시그니처, API 응답 형식, 설정 기본값, CLI 옵션, 데이터 스키마 |
| 삭제 | 파일, 공개 함수, 설정 키, 문서 섹션 |
| 보안·권한·비밀 | 인증·인가 코드, IAM·RBAC, 비밀 값의 위치나 읽는 주체 |
| 검증 우회 | 4절에서 통과로 인정하지 않은 변경 |
| 되돌림 | 3회 실패로 되돌린 단위 |
| 기준선 실패 | 변경 전부터 실패하던 검증 |
| 가정 | 의도가 애매해 가정을 두고 진행한 것, 제안에 없던 변경 |
| 문서 의미 변경 | 사실·수치·절차 순서가 달라진 곳. 문장 다듬기·구조 이동은 해당 없음 |

하나도 해당하지 않고 검증을 통과했으면 개수로만 집계한다. 사람 항목마다 변경 전후, 왜 사람인가, 권장, 확인 방법을 채운다.
