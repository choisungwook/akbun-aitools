# akbun-refactoring-autoverify

이 skill의 목표는 **사람이 읽는 양을 줄이는 것**이다. 변경이 많아도 자동 검증을 통과한 것은 사람에게 가지 않는다. 사람에게 가는 것은 기계가 판정할 수 없는 것만이다.

## 0. 용어

| 용어 | 뜻 |
|---|---|
| 리팩토링 | 이미 사용 중인 것(코드베이스, 문서, 설정, 인프라 코드)을 **동작과 의미를 유지하며** 고치는 것. 새로 만드는 것, 기능을 더하는 것은 리팩토링이 아니다 |
| 검증 | 사람 없이 명령 하나로 통과/실패가 판정되는 것. 테스트, 린트, 타입 검사, 빌드, 포맷 검사, 문서 검사, 스키마 검사 |
| 변경 단위 | 목적이 하나인 변경. 이름 바꾸기 하나, 함수 추출 하나, 문서 섹션 하나 |
| 사람 항목 | 검증으로 판정할 수 없어 작업자가 봐야 하는 변경 또는 사실 |
| 기준선 | 변경 전에 검증을 한 번 돌린 결과. 이미 깨져 있던 것을 내 변경과 구분하는 근거 |

## 1. 보고 채널을 한 번 묻는다

시작할 때 **한 번만** 묻는다. 작업 중에는 다시 묻지 않는다.

| 채널 | 값 | 전달 방법 |
|---|---|---|
| 표준 출력(기본) | `stdout` | 대화 마지막 메시지에 보고서를 그대로 출력 |
| GitHub PR body | `github-pr` | 현재 브랜치의 PR body에 `## 사람이 판단할 것` 섹션을 추가·갱신. PR이 없으면 사용자가 만든 뒤 붙이도록 보고서를 stdout에도 남김 |
| GitHub issue | `github-issue` | 지정한 issue에 코멘트로 추가. 번호가 없으면 새 issue 생성 |
| 파일 | `file:<경로>` | 지정 경로에 Markdown으로 저장 |

질문 예시:

```text
보고 채널을 정해주세요. stdout(기본) / github-pr / github-issue(#번호) / file:<경로>
답이 없으면 stdout으로 진행합니다.
```

규칙:

- 답이 없거나 비대화형 실행이면 `stdout`으로 진행하고 보고 첫 줄에 `채널: stdout(기본값)`을 적는다.
- GitHub 채널을 골랐는데 `gh`나 GitHub MCP가 없으면 `stdout`으로 내려가고 그 사실을 보고 첫 줄에 적는다.
- 채널 질문 외의 의문은 질문하지 않는다. 안전한 가정을 두고 진행하고 그 가정을 사람 항목으로 적는다.

## 2. 범위와 기준선을 잡는다

변경 전에 아래를 확정하고 채팅에 짧게 남긴다.

- 고칠 대상: 파일·디렉터리 목록. 사용자가 말한 범위를 넘지 않는다.
- 유지할 것: 대상이 제공하는 동작, 공개 인터페이스, 문서라면 전달하려는 의미
- 작업 트리 상태: 커밋되지 않은 변경이 있으면 건드리지 않고 사람 항목으로 적는다. stash·reset 하지 않는다.

그다음 3절의 검증 매트릭스를 만들고 **변경 전에 전부 한 번 실행**해 기준선을 얻는다. 기준선에서 이미 실패하는 검증은 그대로 두고 사람 항목에 `기준선 실패`로 적는다. 내 변경으로 고치려 하지 않는다.

## 3. 검증 매트릭스를 만든다

저장소가 이미 쓰는 검증을 먼저 찾는다. 찾는 순서와 대상별 후보는 [`references/verification-catalog.md`](references/verification-catalog.md)를 따른다.

1. 저장소가 정한 것: CI 워크플로우, `Makefile`, `package.json` scripts, `pre-commit`, `pyproject.toml`, 저장소 문서의 검증 절
2. 언어·형식의 표준 도구: 위가 없을 때만
3. 없음: 그 대상은 `자동 검증 없음`으로 표시

표로 정리한다.

| 대상 | 검증 | 명령 | 기준선 |
|---|---|---|---|
| `src/order/` | 단위 테스트 | `pytest tests/order -q` | 통과 |
| `src/order/` | 타입 검사 | `mypy src/order` | 실패 2건(기존) |
| `docs/*.md` | 문서 검사 | `markdownlint docs` | 통과 |
| `deploy/*.yaml` | 없음 | - | - |

규칙:

- `자동 검증 없음`인 대상을 고치면 그 변경은 **전부 사람 항목**이다. 통과했다고 쓸 수 없다.
- 검증이 없어 사람 항목이 지나치게 많아질 것 같으면 가장 작은 검증 하나를 추가할 수 있다(예: 파싱만 확인하는 테스트, `yaml` 로드 검사). 추가한 검증은 그 자체를 사람 항목으로 적는다.
- 검증 명령이 오래 걸리면 변경 단위마다 대상 범위만 돌리고, 마지막에 전체를 한 번 돌린다.

## 4. 작은 단위로 고치고 매번 검증한다

변경 단위 하나마다 아래를 반복한다.

1. 변경한다.
2. 그 대상의 검증을 돌린다.
3. 실패하면 **내 변경의 원인**을 고치고 다시 돌린다.
4. 3번 시도해도 실패하면 그 단위를 되돌리고 사람 항목에 `되돌림`으로 적는다. 실패 출력의 핵심 줄을 함께 남긴다.

검증을 통과시키기 위해 아래를 하면 통과로 인정하지 않고 사람 항목으로 적는다.

- 테스트·기대값·스냅샷·golden 파일을 바꾼 것
- 린트 규칙을 끄거나 `ignore` 주석을 붙인 것
- 검증 명령의 범위를 줄인 것

사용자가 커밋을 요청했으면 변경 단위마다 커밋한다. 요청이 없으면 커밋하지 않는다.

## 5. 사람 항목을 판정한다

변경 단위마다 아래 중 하나에 해당하면 사람 항목이다. 하나도 해당하지 않고 검증을 통과했으면 사람에게 가지 않고 개수로만 집계한다.

| 판정 | 예 |
|---|---|
| 자동 검증 없음 | 검증 수단이 없는 대상의 변경 |
| 동작·인터페이스 변경 | 공개 함수 시그니처, API 응답 형식, 설정 기본값, CLI 옵션, 데이터 스키마가 달라짐 |
| 삭제 | 파일, 공개 함수, 설정 키, 문서 섹션을 지움 |
| 보안·권한·비밀 | 인증·인가 코드, IAM·RBAC, 비밀 값의 위치나 읽는 주체가 달라짐 |
| 검증 우회 | 4절에서 통과로 인정하지 않은 변경 |
| 되돌림 | 3회 실패로 되돌린 단위 |
| 기준선 실패 | 변경 전부터 실패하던 검증 |
| 가정 | 의도가 애매해 가정을 두고 진행한 것 |
| 문서 의미 변경 | 문서 리팩토링에서 사실·수치·절차 순서가 달라진 곳. 문장 다듬기·구조 이동은 해당 없음 |

사람 항목마다 아래 네 가지를 채운다.

- 무엇: 위치(`file:line` 또는 문서 헤더)와 변경 한 줄
- 왜 사람인가: 위 판정 중 무엇인지
- 권장: 작업자가 고를 선택지와 이 skill의 권장 하나
- 확인 방법: 사람이 판단할 때 볼 것(명령, 화면, 문서)

## 6. 보고한다

보고서 형식은 [`references/report-template.md`](references/report-template.md)를 따른다. 순서는 고정이다.

1. 첫 줄: 채널, 범위, 변경 단위 수, 사람 항목 수
2. 사람이 판단할 것: 5절 항목. 없으면 `없음`이라고 쓴다. 이 줄은 생략하지 않는다
3. 자동 검증 통과 요약: 판정별 개수와 검증 명령의 최종 결과 표. 개별 변경은 나열하지 않는다
4. 검증 매트릭스: 3절 표의 최종 상태
5. 하지 않은 것: 범위 밖이라 두고 온 것

1절에서 정한 채널로 전달한다. `github-pr`, `github-issue`는 기존 보고가 있으면 새로 만들지 않고 갱신한다.

## 하지 않는 것

- 테스트를 건너뛰거나 비활성화하거나 기대값을 바꿔 통과시키지 않는다.
- 검증 없이 "문제 없어 보임"으로 통과 처리하지 않는다. 검증이 없으면 사람 항목이다.
- 채널 질문 외의 질문을 하지 않는다. 가정을 적고 진행한다.
- 새 기능을 추가하지 않는다. 범위를 넓히지 않는다.
- 기준선에서 이미 실패하던 것을 고치지 않는다. 사람 항목으로만 남긴다.
- 검증이 실패한 상태로 끝내지 않는다. 되돌리고 보고한다.
- 사람 항목이 없어도 보고를 생략하지 않는다.
