# akbun-refactoring-autoverify

## 동기와 기대

구현이 빨라진 만큼 사람의 이해는 빨라지지 않는다. 이해 없이 "동작하니까" 받아들인 변경은 부채로 남는다. 이 skill은 반복 리뷰에서 사람을 빼되, "문제없음"이라는 말 대신 무엇을 어떤 명령으로 검증했고 증거가 어디 있는지를 남긴다. 기대: 사람이 맥락을 복원하는 비용이 줄고, 한 번에 이해할 범위가 변경 단위 하나로 줄고, 제품 의도와 품질 기준을 정하는 판단은 사람에게 남는다.

## 용어

리팩토링은 이미 사용 중인 코드·문서·설정을 동작과 의미를 유지하며 고치는 것이다. 검증은 사람 없이 명령으로 통과/실패가 판정되는 것이며, 검증이 없는 변경은 통과가 아니다. 사람 항목은 검증으로 판정할 수 없어 사람이 결정할 것이다.

## 흐름

세부 규칙과 표는 [`references/procedure.md`](references/procedure.md)를 반드시 읽고 따른다.

1. 보고 채널을 한 번 묻는다. `stdout`(기본)·`github-pr`·`github-issue`·`file:<경로>`. 무응답이면 stdout.
2. 범위와 계약(유지할 동작, 항상 지킬 조건, 데이터를 읽고 바꾸는 주체)을 적고, 검증 매트릭스를 만들어 기준선을 얻는다.
3. 제안한다. 무엇을 어떤 근거로 수정·삭제·생성할지 목록으로 보이고 수락을 받는다. 계약에 기여하지 않거나 코드와 어긋나거나 참조가 없는 코드·문서·설정은 삭제를 제안한다. 수락 전에는 고치지 않고, 무응답이면 제안서만 보고하고 끝낸다.
4. 수락된 단위마다 변경 → 검증 → 내 원인 수정을 반복하고, 3회 실패면 되돌린다. 테스트·기대값·린트 규칙을 바꿔 통과시키지 않는다.
5. 단위마다 사람 항목인지 판정한다. 검증 없음·동작/인터페이스 변경·삭제·보안·검증 우회·되돌림·기준선 실패·가정·문서 의미 변경.
6. 보고한다. 사람 항목(변경 전후·근거·권장·확인 방법) → 통과 요약 개수 → 매트릭스 → 하지 않은 것. [`references/report-template.md`](references/report-template.md) 순서를 따른다.

## 하지 않는 것

범위 확대와 새 기능, 검증 없는 통과 처리, 수락 없는 변경, 기준선 실패 수정, 검증 실패 상태로 종료, 채널·수락 외 질문.
