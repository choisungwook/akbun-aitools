## 규칙

1. 모든 주장은 등급 하나에 속한다. `[Direct]` 작성자가 글로 썼다(PR 본문, 이슈, 커밋 메시지, 주석, 문서의 명시적 문장). `[Supported]` 간접 증거 여럿이 수렴한다. `[Inferred]` 내 해석이다. `[Speculative]` 다른 설명도 똑같이 맞는다. `[Unknown]` 찾아봤는데 없다.
2. Direct·Supported에는 인용 위치가 붙는다. 없으면 Inferred로 내린다.
3. Inferred·Speculative는 `~로 보인다`, `~와 일치한다`, `한 가지 해석은`으로 쓴다. `because`, `~하려고 설계했다`, `~를 고쳤다`, `팀이 결정했다`는 Direct·Supported에만.
4. 코드를 자기 의도의 증거로 인용하지 않는다. 코드는 동작이지 동기가 아니다.
5. 빈틈은 그럴듯한 추측으로 채우지 않고 "모르는 것"에 적는다. 빈틈이 하나도 없으면 의심한다.
6. 질문에 사용자의 가설이 들어 있으면 후보 하나로만 다룬다. 확인해 주려고 증거를 고르지 않는다.
7. 오늘 말이 되는 코드가 당시에도 그 이유로 쓰였다고 가정하지 않는다. 복사·붙여넣기로 생긴 일관성을 의도로 읽지 않는다.
8. 모순은 둘 다 인용한다. 깔끔한 쪽을 고르지 않는다.

## 출력 (한국어 개조식)

### 찾은 것
- `[Direct]` 주장. 출처: PR #N 코멘트(작성자, 날짜) / 커밋 해시 / `file:line` / 문서 경로. 인용 한 줄.
- `[Supported]` 주장. 증거: 항목 목록과 각각이 보여 주는 것.

### 추론한 것
- `[Inferred]` 완화된 주장. 근거: 증거 A와 B, 추론 단계.

### 경쟁 가설
증거가 여러 이야기에 맞을 때만. 가설 / 지지 증거 / 반대 증거 또는 빠진 증거.

### 모르는 것
답 못 한 질문, 비어 있던 검색(쿼리와 범위), 볼 수 없었던 소스(MCP를 쓰지 않아 실시간 채팅·관측·에러 트래커는 항상 여기 들어간다), 알 만한 사람.

### 본 소스
- 소스 컨트롤: 본 파일·커밋 수·PR 번호
- GitHub: 본 PR·이슈 번호와 검색어
- 저장소 문서: 본 경로와 검색어
- 실시간 채팅 / 관측 / 에러 트래커 / 분석 웨어하우스: 보지 않음. 이 skill은 MCP를 쓰지 않는다. 필요하면 사람에게 묻는다.

### 제약 세트
- Preserve: 지켜야 할 동작·불변식과 그 출처
- Change: 바꿔도 되는 것과 그 근거
- Avoid: 과거에 시도했다 되돌린 것과 그 출처
- Risk: 증거가 얇아 바꾸기 전에 확인할 것

### 확신 요약
두 문장.

## 마지막 점검

찾은 것의 모든 주장에 출처가 있는가. 등급에 맞는 어휘인가. 모순을 조용히 하나 고르지 않았는가. 모르는 것이 비어 있지 않은가. 사용자의 가설을 확인해 준 것은 아닌가. 코드를 의도의 증거로 쓴 곳은 없는가. 하나라도 걸리면 고친 뒤 낸다.
