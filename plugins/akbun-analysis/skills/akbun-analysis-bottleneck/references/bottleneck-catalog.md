# 병목 패턴 카탈로그

`SKILL.md` 2단계에서 코드 관찰을 병목 후보로 바꿀 때 대조하는 표다. 각 행은 코드에서 보이는 신호, 트래픽이 늘 때의 메커니즘, 측정 항목, 해결책 후보, 그 해결책이 새로 만드는 문제 순으로 쓴다. 코드베이스에서 신호를 확인하지 못한 행은 후보에 넣지 않는다.

## 데이터 접근

| 패턴 | 코드 신호 | 트래픽 증가 시 메커니즘 | 측정 항목 | 해결책 후보 (작은 변경부터) | 새로 생기는 문제 |
|---|---|---|---|---|---|
| N+1 조회 | 루프 안 `findById`, lazy loading 접근, 목록 후 건별 조회 | 요청당 쿼리 수가 목록 크기에 비례. 트래픽 N배 × 목록 M건 = N·M 쿼리 | DB queries/request, `pg_stat_statements` calls 상위, APM 트레이스 span 수 | fetch join·`IN` 배치 조회 → DTO 프로젝션 → 캐시 | `IN` 절 크기 상한, 조인 결과 중복 행, 캐시 무효화 |
| 인덱스 없는 조건·정렬 | `WHERE` 컬럼이 인덱스에 없음, `ORDER BY` + `LIMIT`, `LIKE '%x%'` | 테이블 증가와 트래픽 증가가 곱해져 full scan 비용 폭증 | rows scanned/request, `EXPLAIN` seq scan, DB CPU | 인덱스 추가 → 쿼리 조건 재작성 → 검색 엔진 분리 | 쓰기 증폭, 인덱스 빌드 중 락(`CONCURRENTLY` 필요), 저장 공간 |
| `OFFSET` 페이지네이션 | `LIMIT ? OFFSET ?`, 페이지 번호 파라미터 | 뒤 페이지일수록 스캔 행 증가. 크롤러·무한 스크롤에서 심화 | rows scanned/request 페이지별 분포 | 커서(keyset) 페이지네이션 → 페이지 상한 | 임의 페이지 점프 불가, 정렬 키 유일성 요구 |
| `COUNT(*)` 전체 집계 | 목록 API가 총 건수 반환 | 매 요청마다 테이블 전체 스캔 | 쿼리별 평균 시간, 목록 API p99 | 근사치·캐시된 카운트 → 총 건수 제거 | 카운트 부정확, 갱신 지연 |
| 넓은 트랜잭션 | `@Transactional` 안 외부 호출, 트랜잭션 안 파일 I/O | 커넥션 점유 시간 = 외부 호출 시간. 풀 고갈 | pool active/pending, transaction duration p99 | 외부 호출을 트랜잭션 밖으로 → 트랜잭션 분할 | 부분 실패 시 보상 처리, 정합성 창 |
| 행 락·비관적 락 | `SELECT ... FOR UPDATE`, `PESSIMISTIC_WRITE`, 단일 카운터 행 갱신 | 같은 행에 요청이 몰리면 직렬화. 재고·좌석·잔액이 전형 | lock wait time, `pg_locks` 대기 수, deadlock 수 | 낙관적 락 + 재시도 → 원자적 `UPDATE ... SET x = x - 1 WHERE x > 0` → 큐로 직렬화 | 재시도 폭증(retry storm), 재고 초과 판매 방지 검증, 큐 지연 |
| 커넥션 풀 상한 | `maximumPoolSize`, `pool_size` 설정, 서비스 인스턴스 수 | 인스턴스 × 풀 크기가 DB `max_connections`에 닿음 | pool pending, DB active connections, connection wait timeout 수 | 풀 크기 조정 → 쿼리 시간 단축 → pgbouncer 같은 풀러 | 풀러 트랜잭션 모드 제약(prepared statement), 스케일아웃 시 총량 재계산 |
| 단일 DB 공유 | 여러 MSA가 같은 DB·스키마 접속 | 한 서비스 트래픽이 다른 서비스 지연을 만듦 | 서비스별 DB CPU 기여, 서비스별 쿼리 수 | 읽기 복제본 분리 → 서비스별 스키마·DB 분리 | replication lag stale read, 분산 트랜잭션 부재, 조인 불가 |
| 핫 파티션·핫 키 | 시간순 PK, 단일 테넌트 키, 인기 상품 하나 | 특정 파티션·노드로만 트래픽 집중 | 파티션별 QPS 편차, 단일 키 read/write 비율 | 키 salt·분산 → 캐시 → 파티션 재설계 | 조회 시 salt 재조합, 캐시 스탬피드 |

## 서비스 간 호출

| 패턴 | 코드 신호 | 트래픽 증가 시 메커니즘 | 측정 항목 | 해결책 후보 (작은 변경부터) | 새로 생기는 문제 |
|---|---|---|---|---|---|
| 동기 체인 호출 | A→B→C HTTP/gRPC 연속 호출, 타임아웃 미설정 | 지연 합산, 한 서비스 지연이 상위 전체 스레드를 점유 | 서비스별 p99, 스레드 풀 active, 호출 depth | 타임아웃·재시도 상한 설정 → 병렬 호출 → 비동기·이벤트 | 타임아웃 시 부분 응답 처리, 재시도 폭증, 이벤트 순서·중복 |
| 팬아웃 호출 | 한 요청이 K개 서비스 호출, 목록 각 항목마다 호출 | 요청당 외부 호출 K배. 하위 서비스에 트래픽 증폭 | outbound calls/request, 하위 서비스 inbound QPS | 배치 API → 응답 조합 캐시 → BFF·집계 서비스 | 배치 크기 상한, 캐시 일관성, 새 서비스 운영 |
| 재시도 폭증 | 재시도 무제한, 지수 백오프 없음, 클라이언트·서버 양쪽 재시도 | 실패 시 트래픽 배수 증가. 회복 방해 | retry count/request, 실패 시 inbound QPS 배수 | 재시도 상한 + 지터 백오프 → 서킷 브레이커 → 부하 차단(load shedding) | 서킷 open 시 폴백 정의, 정상 요청까지 차단 |
| 외부 API 한도 | 서드파티 호출(결제·문자·지도) rate limit, 단일 API 키 | 트래픽이 외부 한도에 먼저 닿음. 429·지연 | 외부 호출 QPS, 429 비율, 외부 p99 | 응답 캐시 → 호출 합치기·비동기화 → 키 분산·계약 상향 | 캐시 신선도, 비동기 결과 전달 경로, 비용 |
| 스레드·워커 상한 | `server.tomcat.threads.max`, `workers`, Node 단일 이벤트 루프의 CPU 작업 | 동시 요청이 워커 수를 넘으면 큐잉·타임아웃 | 워커 active/queued, 이벤트 루프 lag | 워커 수 조정 → 블로킹 제거·비동기 I/O → 스케일아웃 | 워커 증가 시 DB 커넥션 총량, 메모리 |

## 캐시와 상태

| 패턴 | 코드 신호 | 트래픽 증가 시 메커니즘 | 측정 항목 | 해결책 후보 (작은 변경부터) | 새로 생기는 문제 |
|---|---|---|---|---|---|
| 캐시 없음 | 같은 읽기 반복(설정·상품·프로필) 매번 DB | 읽기 QPS가 그대로 DB에 도달 | read/write 비율, 동일 키 반복 조회 비율 | 로컬 캐시 → 분산 캐시(Redis) | 무효화 정책, 인스턴스 간 불일치, 캐시 미스 시 DB 부하 |
| 캐시 스탬피드 | TTL 동일 만료, 미스 시 즉시 DB 조회 | 만료 순간 동시 요청이 모두 DB로 | 캐시 miss 비율 스파이크, 만료 직후 DB QPS | TTL 지터 → 락·single-flight → 백그라운드 갱신 | stale 허용 범위, 갱신 실패 시 처리 |
| 인메모리 상태 | 싱글턴 Map, 세션 메모리, 프로세스 로컬 카운터 | 스케일아웃 시 인스턴스별 불일치, 스티키 세션 필요 | 인스턴스 간 값 불일치, 메모리 증가율 | 외부 저장소(Redis)로 이동 → 무상태화 | Redis가 새 단일 장애점, 네트워크 왕복 추가 |
| 큰 응답·직렬화 | 엔티티 전체 반환, 중첩 JSON, 이미지 base64 | 요청당 CPU·네트워크가 응답 크기에 비례 | 응답 바이트/request, 직렬화 CPU 시간 | 필드 선택 DTO → 압축 → 페이징 | 클라이언트 호환성, 압축 CPU |

## 비동기와 큐

| 패턴 | 코드 신호 | 트래픽 증가 시 메커니즘 | 측정 항목 | 해결책 후보 (작은 변경부터) | 새로 생기는 문제 |
|---|---|---|---|---|---|
| 컨슈머 처리량 | 단일 컨슈머, 파티션 1개, 메시지당 DB 쓰기 | 생산 속도 > 소비 속도. lag 누적 | consumer lag, 메시지당 처리 시간 | 배치 소비 → 파티션·컨슈머 증가 → 처리 로직 경량화 | 순서 보장 약화, 리밸런싱 중 중단, 중복 처리 |
| 동기 후처리 | 요청 안에서 메일·알림·감사 로그 전송 | 부수 작업 지연이 사용자 응답에 합산 | 요청 안 부수 작업 시간 비율 | 비동기 스레드 → 큐 발행 | 실패 시 유실(outbox 필요), 최종 일관성, DLQ 운영 |
| 스케줄러 단일 실행 | `@Scheduled`, cron 배치가 전체 테이블 처리 | 데이터 증가로 배치 시간이 주기를 넘음. 스케일아웃 시 중복 실행 | 배치 소요 시간/주기 비율, 처리 행 수 | 청크 처리 → 분산 락 → 이벤트 기반으로 전환 | 락 저장소 의존, 부분 실패 재시작 |

## 개선 뒤 공통으로 옮겨가는 병목

개선은 병목을 없애지 않고 옮긴다. 아래는 해결책 유형별로 다음 병목이 나타나는 자리다. 3-5의 "다음 병목" 한 줄을 쓸 때 참고한다.

- **스케일아웃**: DB 커넥션 총량, 공유 캐시·큐, 외부 API 한도로 이동
- **캐시 도입**: 캐시 서버 메모리·네트워크, 무효화 경로, 미스 시 DB 부하 스파이크로 이동
- **읽기 복제본**: replication lag, 쓰기 마스터 단일 지점으로 이동
- **비동기·큐**: 컨슈머 처리량, 큐 적체, 재처리·중복 처리 로직으로 이동
- **인덱스·쿼리 최적화**: 쓰기 경로·인덱스 유지 비용, 다음으로 무거운 쿼리로 이동
- **타임아웃·서킷 브레이커**: 폴백 경로의 정확성, 부분 실패 상태의 사용자 경험으로 이동
