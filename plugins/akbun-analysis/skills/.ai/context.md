# AI Context

## 작업 맥락

akbun-analysis skills는 코드가 어떤 비즈니스를 위해 쓰였고 그 비즈니스에 어떤 코드가 엮여 있는지를 repo 바깥에 영구 저장하고 시각화한다. 코드 품질 평가가 아니다. `analysis.json`만 분석 원본이며 self-contained HTML과 선택적 draw.io는 JSON에서 생성한다. 이후 업무·구조·역할·영향 가능성 질문은 JSON을 먼저 읽고, 코드 변경은 file:line 근거와 소유 경로를 이용해 증분 반영한다.

## 용어 정리

- 분석 원본: 프로젝트별 `analysis.json`. SQLite와 wiki는 사용하지 않는다.
- 파생 산출물: `analysis.json`에서 생성하는 `analysis.html`과 선택적 `analysis.drawio`. draw.io 변경은 JSON으로 역동기화하지 않는다.
- 활용 모드: JSON을 먼저 읽어 질문에 답하는 기본 모드. 최초 분석과 증분 갱신에서만 코드를 탐색한다.
- 도메인(business): 주문·결제처럼 업무 영역 한 덩어리. HTML 왼쪽 ToC의 상위 항목이다.
- 플로우(flow): 진입점 하나에서 시작해 끝나는 업무 시나리오. `entry`와 실행 순서대로 나열한 `steps`로 이뤄진다.
- layer: 컴포넌트가 흐름의 어느 단계인지. entrypoint, application, domain, infrastructure, external 다섯 개가 전부이며 최대 depth 5의 근거다.
- module: 서비스 안에서 흐름의 한 단계를 맡는 코드 경계. 클래스·함수 단위가 아니라 흐름을 말로 설명할 때 이름을 부를 만한 단계만 만든다.
- origin: 컴포넌트가 어디 소속인지. git(저장소), database(engine 필수), code(현재 코드베이스 경로) 셋뿐이며 HTML 노드 아이콘의 근거다.
- 서비스 관계도: module을 접어 서비스·저장소·외부 시스템 사이 관계만 남긴 화면. 접힌 관계는 지나온 근거를 모두 들고 있다.
- API: 이 프로젝트가 제공하거나 부르는 호출 주소. entrypoint는 시스템 밖에서 직접 들어오는 주소이며 부하분석의 요청량 입력 단위다.
- capacity: 배포 매니페스트에서 읽은 레플리카 1대 기준 자원. 확인 못 하면 넣지 않고, 가정값은 source를 assumed로 둔다.
- fan_out: 부모 요청 1건당 그 관계가 실행되는 횟수. 반복시키는 것이 코드에 보일 때만 1보다 크게 쓴다. 부하가 선형이 아닌 이유다.
- 부하 전파: fan_out 곱셈으로 요청량을 하류로 퍼뜨리고, 사용률이 1에 가까울 때 늘어나는 대기를 동기 호출 경로로 되돌려 합친 결과. 요청당 CPU·메모리는 가정값이라 실측 용량 산정이 아니다.
- layout: 사용자가 HTML에서 드래그한 노드 위치. 분석 결과가 아니므로 직접 만들지 않고 사용자가 준 값만 넣는다.
- project-id: repo이름 slug + git remote(없으면 절대경로) sha256 앞 8자리. 같은 repo는 항상 같은 저장소로 이어진다.
- 영향 가능성: 관계 방향과 종류로 계산한 도달 가능성. 장애 범위나 실제 리스크를 의미하지 않는다.
