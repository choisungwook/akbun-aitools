# akbun-analysis-gitdiff-blast-radius

변경이 diff 밖 어디를 깨는지 머지 전에 찾는다. 대상은 PR 번호, 브랜치, 커밋 범위, 작업 트리의 diff 중 하나다. 두 질문에 답한다. **이 PR을 머지하면 diff 밖 어디가 깨지나. 내 다음 작업과 어디서 만나나.**

`akbun-analysis-git-whyandhow`와 짝이다. why-how가 "왜 이렇게 됐고 어떻게 도나"를 읽고, 이 skill은 "바꾸면 무엇이 깨지나"를 실행으로 확인한다. GitHub는 `gh` CLI만 쓰고 MCP 도구는 쓰지 않는다. 저장소 파일은 증명 스크립트를 제외하고 고치지 않는다.

## 원칙

- **그럴듯한 글은 무가치하다.** 영향 분석 글은 맞아도 틀려도 똑같이 설득력 있게 읽힌다. 그래서 글을 넘기지 않고, 전체가 의존하는 사실 한두 개를 골라 코드를 실행해 증명한다.
- **호출자 나열은 일이 아니다.** 호출자는 grep이 1초에 찾는다. 일은 grep이 못 보는 파손이다.
- **확신 사다리.** 안전을 지지하는 사실마다 어디까지 올라갔는지 적는다. 1 말했다(무가치). 2 `file:line`이나 라이브러리 소스를 지목했다. 3 실패 경로를 단계별로 걸어 봤고 닿지 않는다. 4 실행했다(실제 코드를 부르고 틀리면 크게 실패하는 스크립트·테스트). 5 실행 중인 앱에서 재현했다. 4에 못 간 사실은 `미증명`으로 쓴다. 확정된 것처럼 쓰지 않는다.

## 1. 변경을 읽는다

- PR이면 `gh pr view <n> --json title,body,files,commits,reviews,comments`와 `gh pr diff <n>`. 브랜치·커밋이면 `git diff <base>...<head>`. 작업 트리면 `git diff`와 `git status`.
- 추가·변경·삭제된 심볼을 목록으로 만든다. diff가 명시하지 않는 동작 변화(기본값, 순서, 타이밍, 예외 경로, 직렬화 형태)를 따로 적는다.
- 동기와 제약이 필요하면 `akbun-analysis-git-whyandhow`의 1~3단계(앵커, why 조사, 제약 세트)를 먼저 돈다. Preserve와 Avoid가 이 skill의 위험 후보 1순위다.

## 2. 안전한 이유인 단 하나의 사실을 찾는다

위험해 보이는 변경 대부분은 사실 하나 때문에 안전하다. "이 호출은 이미 만료된 캐시 항목만 지우고 다른 일은 하지 않는다", "이 필드는 직렬화되지 않는다", "이 경로는 flag가 꺼진 상태에서는 도달하지 않는다". 그 사실을 찾는다. 맞으면 위험 후보 대부분이 한 번에 지워진다. 시간을 여기에 쓴다. 가능성 목록을 길게 쓰는 데 쓰지 않는다.

사실이 둘 이상 필요하면 둘 다 적되, 셋을 넘으면 변경이 크다는 뜻이다. 6단계(여러 모델)로 간다.

## 3. grep이 멈추는 곳을 본다

- 호출하는 라이브러리의 소스와 고정 버전(lockfile), 로컬 패치.
- 실행 시점. 마이크로태스크, 언마운트·해체 순서, 이벤트 루프 단계, 프레임워크별 렌더 타이밍.
- 심볼 검색이 놓치는 것. API가 돌려주는 JSON 형태, DB 컬럼과 마이그레이션, wire format과 프로토콜 버전, 같은 바이트를 읽는 다른 언어·서비스, feature flag와 설정값, 세 홉 아래의 소비자, 로그·메트릭 파서.
- 다음 작업과의 접점. 사용자가 계획 중인 작업이나 열린 브랜치가 같은 파일·심볼·데이터를 만지면 그 지점을 따로 적는다.

## 4. 위험을 정직하게 매긴다

- 남길 것은 확인된 위험만. 각각 어떻게 깨지는지, `file:line`, 일어날 확률과 일어나면 드는 비용, 확인 방법.
- 확인해서 지운 것은 따로 목록에 둔다. 다음 리뷰어가 같은 걸 다시 의심하지 않게.
- 근거는 `file:line`, 커밋, PR·이슈 번호. 검색해서 없었던 것도 답이다. 호출자나 API를 지어내지 않는다.

## 5. 사실을 실행으로 증명한다

앱이 쓰는 것과 같은 라이브러리를 import해 걱정되는 그 함수를 정확히 부르는 작은 스크립트나 테스트를 쓴다. 틀리면 크게 실패하게 만든다. 실행하고 출력을 그대로 붙인다.

- 스크립트는 저장소의 관례(테스트 디렉터리, 스크립트 디렉터리)에 두거나, 관례가 없으면 임시 디렉터리에 두고 경로를 보고에 적는다. 저장소에 남길지는 사용자가 정한다.
- 싸게 증명할 수 없으면 `미증명`으로 표기하고, 무엇이 있으면 증명할 수 있는지(환경, 데이터, 권한) 적는다.

## 6. 큰 변경은 여러 모델로

변경이 넓거나 사실이 셋을 넘으면 같은 질문을 서로 다른 모델의 Agent 2~3개에 병렬로 묻고 답을 합친다. 모델마다 다른 실제 버그를 잡는다. 합칠 때 겹치는 위험은 신뢰를 올리고, 한 모델만 낸 위험은 코드로 확인한 뒤 남긴다.

## 7. 보고

한국어 개조식. 이 순서를 지킨다.

1. **무엇이 바뀌나.** diff에 명시된 것과 명시되지 않은 동작 변화.
2. **안전한 이유인 사실.** 사실, 사다리 단계, 증명(스크립트 경로와 출력). 못 증명했으면 `미증명`과 이유.
3. **위험.** 확인된 것만. 어떻게 깨지는지, `file:line`, 확률·비용, 확인 방법. 중요한 것은 증명 첨부.
4. **확인해서 지운 것.** 무엇을 봤고 왜 괜찮은지.
5. **다음 작업과의 접점.** 사용자의 계획·열린 브랜치와 만나는 파일·심볼·데이터. 없으면 "없음".
6. **머지 전에 돌릴 것.** 진짜 버그를 잡는 가장 싼 테스트나 재현, 작성한 스크립트.

공개 채널에 낼 때는 비밀값과 내부 URL을 지운다.

## 옵션: PR 코멘트

사용자가 요청("PR에 코멘트 달아", "--comment")했을 때만 한다. 요청이 없으면 대화창에만 보고한다.

- 보고 1~6을 그대로 Markdown으로 만들어 `gh pr comment <n> --body-file <file>`로 단다. 본문을 인자로 직접 넘기지 않는다. 따옴표와 코드 블록이 깨진다.
- 코멘트 첫 줄은 `## Blast radius`, 마지막에 증명 스크립트 경로와 실행 명령을 둔다.
- 같은 PR에 이미 이 skill의 코멘트가 있으면 새로 달지 않고 `gh api`로 그 코멘트를 수정한다. 코멘트 ID는 `gh pr view <n> --json comments`에서 `## Blast radius`로 시작하는 것을 찾는다.
- 달기 전에 본문을 사용자에게 한 번 보이고 확인을 받는다. 외부에 남는 글이다.
