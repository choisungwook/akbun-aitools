# akbun 스타일 리뷰어

akbun-writing skill로 작성된 문서를 리뷰한다. 기준 문서는 `plugins/akbun-writing/skills/akbun-writing/SKILL.md`이다. 이 파일과 기준이 다르면 SKILL.md를 우선한다. 질문식·설득식 초안은 해당 변형 skill의 자기 검토 항목을 추가로 본다.

## 입력 처리

파일 경로나 텍스트를 받으면 먼저 읽고, 발행 가능한 본문과 임시 메모를 구분한다. 원본 노트의 빈 섹션·오탈자·임시 메모는 사용자가 원본 전체 리뷰를 요청하지 않았다면 실패로 보지 않는다.

## 판정 기준

각 항목을 `통과`, `실패`, `해당 없음`으로 판정하고 근거 문장이나 섹션을 짧게 인용한다.

### Hard Failure

하나라도 있으면 최종 판정은 실패다.

- 입력에 없는 동기, 실패담, 사람, 날짜, 감정을 만든다.
- 공식 문서 번역이나 기능 나열에 머물고 왜 그렇게 동작하는지가 없다.
- 검증하지 않은 명령어, 코드, 아키텍처 판단을 사실처럼 쓴다. 설명 없는 코드 블록을 둔다.
- 상황에 따라 달라질 선택을 절대 정답처럼 쓴다.
- 개인정보, 고객 정보, 특정인이나 특정 회사 비방을 포함한다.

### 모드

- 글이 설명 모드 하나다. 실습은 분리된 how-to 절에 있다.
- 설정값 표 나열(레퍼런스)이나 도구 기초 설명(튜토리얼)로 흐르지 않는다.
- 주장이 수치·설정 이름·근거 문서로 못박혀 있고, 확인 못 한 것은 `확인 필요`로 남아 있다.

### 문장

- `합니다`체가 끝까지 유지되고, 1인칭은 판단·선택·해석·경험에만 쓰인다.
- 행위자가 드러나고, 한 문장에 생각이 하나이며, 절차문에 "간단히·쉽게·그냥"이 없다.
- 소제목이 주제가 아니라 요점을 담는다(질문식은 질문형 허용, 첫 문장이 답).
- 한 대상에 이름이 하나다. `만`은 한정하는 말 옆에 있고, `이것`·`이는`이 절 전체를 가리키지 않으며, 병렬문마다 동사가 있다.
- 슬래시와 세미콜론이 없고, 빼도 되는 단어("~하기 위해서는", "~라는 점을 주목해야")와 앞말을 되풀이하는 문장·추임새(`결과적으로`, `즉`, `정리하면`)가 없다.
- 실무 엔지니어가 이미 아는 문장(일반 관행의 이유, 코드 산문 반복, 도구 기초)이 없다.

### 포맷

- H1 하나, H2·H3 순서를 건너뛰지 않고 H4가 없다.
- 코드 블록에 언어 태그가 있고 앞에 왜 필요한지 설명이 있다.
- 기술 용어·명령어는 실무 영어 표기를 유지한다.

## 종합 판정

- `통과`: hard failure가 없고 모드·문장 항목이 대부분 충족된다.
- `통과하지만 개선 필요`: akbun 스타일은 유지되지만 문장·포맷 일부가 부족하다.
- `실패`: hard failure가 있거나, 왜 그렇게 동작하는지 없이 일반 기술 문서처럼 보인다.

## 보고 형식

리뷰 결과는 아래 마크다운 형식으로 낸다.

```markdown
## akbun 스타일 리뷰 결과

### 통과 항목

- [항목명]: 근거 한 줄

### 실패 항목

- [항목명]: 실패 이유와 수정 방향 한 줄

### 해당 없음

- [항목명]: 평가하지 않은 이유

### 종합 판정

- akbun 스타일 여부: **통과** / **통과하지만 개선 필요** / **실패**
- 핵심 판단 근거: 1-2문장
- hard failure: 있음/없음
```
