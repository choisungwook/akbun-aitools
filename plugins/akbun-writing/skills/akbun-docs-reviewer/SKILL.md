# 기술 문서 리뷰

## 목표

**입문자가 다시 읽지 않고도 원리를 따라갈 수 있고, akbun의 목소리는 그대로 남은 글로 만든다.** 둘이 충돌하면 목소리를 남긴다.

이 목표를 네 개로 쪼갠다. 위에서 아래 순서로 본다. 구조가 틀린 글은 문장을 다듬어도 살아나지 않는다.

1. 독자가 입구에서 "읽을지" 판단한다 -> `서론과 결론`, `정보 구조`
2. 한 번 읽고 이해한다 -> `문장과 문단`
3. 같은 개념을 항상 같은 말로 부른다 -> `용어`
4. 화면에서 구조가 한눈에 보인다 -> `Markdown 포맷`

`akbun 스타일 보존`은 네 목표 전부에 걸리는 제약이므로 먼저 읽는다. 고친 결과는 `변경 사항 보고`로 닫는다.

검토 대상은 `.md`, `.hcl`, `.tf`다. 모든 출력은 한국어로 쓰고, git 명령어는 실행하지 않는다. 새 글 작성, 번역, 요약, Markdown 변환, Notion 동기화는 하지 않는다. 기술적 오류를 발견하면 문체 문제와 별도로 표시한다. 상세 Don't/Do 예시는 `references/readability-review.md`에 있다.

## 제약: akbun 스타일 보존

목표: 잘 읽히게 고치는 과정에서 akbun의 목소리를 지우지 않는다. 아래는 잘 읽힘을 이유로 건드리지 않는다.

- 1인칭 경험과 판단(`저는`, 실패담, `식은땀` 같은 솔직한 표현)을 객관적 매뉴얼 문체로 바꾸지 않는다. 능동형으로 고치라는 것은 어색한 수동태를 푸는 것이지, 경험의 주인을 지우는 게 아니다
- 차분한 존댓말(`합니다`체)을 유지한다
- 원리를 파고드는 깊이와, 트레이드오프로 닫는 구조를 살린다. 간결하게 고치라는 것은 군더더기를 빼라는 것이지 원리의 근거를 빼라는 게 아니다
- 판단을 거부하는 표현(`무조건 X인 것은 아니다`, `정답은 없다`)은 akbun의 패턴이므로 메타 담화로 오해해 지우지 않는다

## 목표 1-a: 서론과 결론

목표: 서론 15초 안에 "이 글이 내 문제를 다루는가"가 판단되고, 결론에 남을 것 하나가 있다.

사용자가 넘긴 내용을 **본문**으로 가정한다. 서론과 결론은 그 본문을 읽고 새로 쓰는 부분이며, 정해진 틀·문장 패턴·필수 문구가 없다.

- 서론은 15초 분량(150자 안팎, 두세 문장)으로 쓴다. 본문이 무엇을 다루는지 알려주면서 계속 읽고 싶게 만든다. 둘 중 하나만 있으면 부족하다
- 서론은 한 번에 이해되는 문장으로 쓴다. 한 문장에 하나의 뜻만 담고, 수식이 겹치면 문장을 나눈다
- 결론은 본문을 다 읽은 독자에게 남길 것 하나로 닫는다. 길이와 형식을 고정하지 않는다
- 본문에 없는 동기·실패담·감정·수치를 지어내지 않고, 본문 요약을 되풀이하지 않는다. 억지스러운 서론·결론의 주된 원인이다
- 분량을 채우려고 문장을 늘리지 않는다. 남길 것이 없으면 짧게 닫는다

## 목표 1-b: 정보 구조

목표: 글 전체가 하나의 목표를 향하고, 다음에 무엇이 나올지 독자가 예측한다. 블로그 글, README, 가이드에 적용하고 Terraform·HCL 같은 설정 파일에는 적용하지 않는다.

- 가치 먼저: 도입이 기능·세부 설정·배경 역사부터 시작하지 않는가? akbun 글에서 독자가 얻는 가치는 보통 "원리를 알면 실무에서 무엇이 달라지는지"다
- 효과적인 제목: 핵심 키워드가 있고 30자 안팎으로 짧으며 평서문인가? 물음표·느낌표로 끝나거나 내용을 추측하게 만드는 제목은 구체적 키워드를 넣어 다시 쓴다
- 한 목표 집중: 제목이 H4(`####`)까지 깊어지거나 핵심 주제가 둘 이상이면 글 분리를 제안한다
- 예측 가능한 구조: 같은 수준의 제목이 같은 패턴(동사형/명사형)을 따르는가? 정보가 기본 개념 -> 상세 -> 예제 순으로 배치됐는가
- 자세히 설명: 새 개념이 처음 등장할 때 한두 문장으로 정의하는가? 기능이 어떤 조건에서 어떻게 동작하는지(입력·상태·시간에 따른 차이) 충분히 설명하는가

## 목표 2: 문장과 문단

목표: 입문자가 문장을 두 번 읽지 않는다.

- 맞춤법과 문법 오류를 함께 잡는다
- 두 줄이 넘는 문장은 나누고, 의도가 불명확한 문장은 다시 쓴다. 주어와 서술어를 가까이 붙이고, 수동태보다 능동태를 쓴다
- 메타 담화 최소화: '앞서 설명했듯이', '다음으로 알아보겠습니다', '결론적으로', '사실은', '아시다시피' 같은 '말에 대한 말'은 지우고 핵심 메시지만 남긴다
- 구체적으로 쓰기: 동사에서 파생된 명사(`설정 수행`)보다 동사(`설정합니다`)를 쓰고, `가능성이 있다`·`많을 때` 같은 모호한 표현은 사실·수치로 바꾸며, 누가·무엇을·어디에·어떻게가 빠지지 않았는지 확인한다
- 자연스러운 한국어: 불필요한 한자어(`삭제하는 작업을 수행합니다` -> `삭제합니다`)와 영어식 명사형 번역체(`인증 처리가 완료된 후` -> `인증한 후`)를 고친다
- 한 문단에 하나의 아이디어, 최대 3~4 문장으로 두고 문단 사이에 빈 줄을 넣는다. 블로그에서 HTML로 렌더링되므로 이어지는 긴 문단은 텍스트 벽이 된다
- 코드 블록 다음에는 이전 문단을 이어가지 않고 새 문단을 시작한다. 관련 항목이 3개 이상이면 산문보다 목록이 낫다

## 목표 3: 용어

목표: 같은 개념이 문서 어디에서나 같은 표기로 나온다.

- 아래 목록에 없는 용어는 업계 표준 관례(공식 문서, RFC, 주요 프로젝트)를 따라 문서 전체에서 통일하고, 결정과 이유를 보고한다
- 고유명사(제품·프로젝트 이름)는 원래 언어와 표기를 유지하고, 약어는 첫 등장 시 풀어 쓴다(`SSR` -> `SSR(Server-Side Rendering)`)
- 한국어가 더 명확하면 한국어, 영어가 표준 용어면 영어를 쓴다. 같은 개념을 여러 단어로 바꿔 쓰지 않는다
- 소문자 사용: cilium, node, pod, kubernetes, envoy, envoy proxy, gateway, canary, blue/green, weight, kind cluster
- 원래 표기 유지: eBPF, IPAM, CLI, NAT, DNAT, SNAT, MetalLB, Gateway API, TLS, HTTP, HTTPS, TCP, UDP, IP, GatewayClass
- 영어 사용: map (eBPF 맥락), LoadBalancer, deployment, service (Kubernetes 리소스), TLS termination, self-signed certificate
- 한국어 사용: 백엔드, 프론트엔드 (애플리케이션 레이어), 인프라 (IT 인프라 맥락)
- 예외: 문장 첫 단어는 대문자로 시작한다. 코드 블록 내부는 검사하지 않는다

## 목표 4: Markdown 포맷

목표: 강조가 진짜 중요한 곳에만 남아, 훑어보는 독자에게 구조가 보인다.

- 목록 — 중첩 목록 포함 모든 목록에 하이픈(`-`)을 사용한다
- 이미지 — `![이미지설명](path/to/image.png "이미지설명")` 형식을 따른다. alt 텍스트가 없으면 확장자를 제외한 파일명을 사용한다
- 코드 블록 — 앞에 빈 줄을 넣고 언어 식별자(`bash`, `hcl`, `yaml`, `text` 등)를 포함한다
- 들여쓰기 — 2칸 공백을 쓰되, 언어 자체 관례가 있으면(예: Python은 4칸) 그 관례를 따른다
- 헤더 — 1~2 문장짜리 내용에는 헤더를 두지 않는다. 같은 레벨 헤더가 5개 이상 연속이면 병합하거나 목록으로 대체하고, H4 이상(`####`)은 굵은 글씨나 목록으로 평탄화한다
- 굵은 글씨 — 섹션당 1~2개만 쓴다. 목록 항목에서는 핵심 키워드만 굵게 표시한다
- 백틱 — 명령어, 파일명, 리소스 이름, 설정 키에만 쓴다. 강조는 굵은 글씨로 한다

## 변경 사항 보고

목표: 사용자가 원문과 달라진 지점을 되짚을 수 있다. 아래는 반드시 보고한다.

- 삭제한 문장이나 문단
- 의미가 바뀐 재작성
- 주요 용어 변경과 구조 재편
- 목록에 없는 용어 통일 결정 (예: "docker -> Docker로 공식 브랜딩에 맞게 통일")
