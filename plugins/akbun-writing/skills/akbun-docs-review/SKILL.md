# 기술 문서 교정

## 목표

원문의 내용, 문체, 레이아웃을 유지하면서 표기 불일치와 명백히 잘못된 사실을 바로잡는다. 이 skill은 정확성(맞는 말인가)을 맡고, 문장 품질(사람 말인가)은 `akbun-writing-naturalize`가 맡는다. 맞춤법·띄어쓰기·오탈자·어색한 문장 규칙을 여기에 다시 적지 않는다.

Markdown처럼 사람이 읽는 텍스트 문서를 대상으로 한다. 코드, 설정 파일, 번역, 요약, 새 글 작성, 문서 구조 변경은 대상이 아니다.

## 교정 범위

- 제품명, 프로젝트명, 프로토콜명, 약어의 공식 표기와 대소문자
- 같은 의미로 쓰인 용어의 문서 내 표기 불일치. 하나의 대상에 하나의 이름
- 기술적 사실, 수치, 예제의 동작 중 근거가 있는 오류

표기를 통일할 때는 문서 안에서 가장 많이 쓰인 표현보다 공식 표기와 해당 기술 분야의 관례를 우선한다.

## 보존 범위

보호 영역은 `akbun-writing-naturalize`의 `우선순위와 보호 영역` 목록을 그대로 따른다. 거기에 더해 다음을 바꾸지 않는다.

- 헤더 순서, 문단 순서, 목록, 이미지, 코드 블록 등 레이아웃
- 문체, 말투, 글쓴이의 경험과 주장, 설명의 깊이

교정으로 문장 의미가 달라질 가능성이 있으면 원문을 유지하고 `확인 필요`로 보고한다.

## 근거의 기준

사실을 고치려면 다음 중 하나가 있어야 한다. 없으면 고치지 않고 `확인 필요`로 보고한다.

- 공식 문서의 URL과 해당 문장
- 실제 실행 결과. 실행 가능한 명령·예제·수치는 실행해서 확인한다
- 저장소 코드의 `file:line`

"일반적으로 그렇다"는 근거가 아니다. 코드를 수정해야 바로잡을 수 있는 오류도 문서에서 고치지 않고 보고한다.

## 처리 절차

1. 원문을 읽고 용어 후보 목록과 사실 주장 목록을 만든다. 파일이 git 추적 대상이 아니면 덮어쓰기 전에 한 줄 경고하고 진행한다.
2. 표기를 통일하고, 근거 기준을 충족한 사실 오류를 고친다.
3. 2단계 결과 본문에 `akbun-writing-naturalize`의 규칙 파일(`references/common-rules.jsonl`, `references/user-rules.jsonl`)과 처리 절차(맞춤법 교정 → 국소 자연화 → 원문 대조)를 호출 모드로 적용한다. 원문 대조의 기준은 원본이 아니라 2단계 결과 본문이다. 2단계에서 고친 표기·사실·수치를 의미 변경으로 되돌리지 않는다.
4. 최종 본문을 원본 파일에 덮어쓴다. `{stem}-v1` 같은 새 파일을 만들지 않는다. 대화창에 붙여 넣은 글은 교정한 전체 글을 대화창에 반환한다.

긴 글은 `akbun-writing-naturalize`의 `긴 글` 절을 따른다.

## 보고

덮어쓰기로 diff가 남지 않으므로 보고가 변경 기록이다. 다음 순서로 대화창에 보고한다.

1. 용어표. 원문 표기 → 통일 표기 → 근거. 통일한 것이 없으면 생략한다.
2. 사실 교정 목록. 위치, 변경 전후, 근거(URL·실행 결과·`file:line`).
3. naturalize 변경 목록. 위치, 변경 전후, 적용한 규칙 `id`(맞춤법 교정은 `spelling`).
4. `확인 필요`. 위치, 수정하지 않은 내용, 판단 근거, 확인이 필요한 이유.

고칠 곳이 없으면 파일을 건드리지 않고 `수정할 부분 없음`이라고 보고한다.
