# 인프라 운영 작업 공지

개발·스테이징에서 검증을 끝낸 인프라 변경을 운영에 적용하기 전, 개발자에게 보내는 문서다. 독자는 인프라 담당이 아니라 **그 인프라 위에서 서비스를 만드는 개발자**다. 독자가 5분 안에 알아야 할 것은 셋이다. 내 서비스에 무엇이 달라지나, 내가 해야 할 일이 있나, 작업 중·후에 무엇을 확인해야 하나. 왜 하는지와 절차·롤백·비용은 그 뒤에 온다.

인터뷰는 자료에 없는 것만 한다. 사용자가 넘긴 변경 내용, 스테이징 결과, 티켓, 다이어그램, 비용 견적을 먼저 읽고, 빈 곳만 한 번에 5개 이하로 묻는다. 2라운드 안에 끝내고 남은 빈칸은 `확인 필요`로 둔다. 수치·시간·비용을 지어내지 않는다.

## 원칙

- **영향을 먼저, 구현은 나중에.** 첫 화면은 "개발자에게 무엇이 달라지나"다. 인프라 내부 세부(어떤 모듈을 어떻게 바꾸는지)는 개발자가 알아야 할 때만 쓴다.
- **주장마다 근거의 성격을 같은 문장에 붙인다.** `측정`(스테이징 실측, 모니터링 수치), `인용`(공식 문서, 단가표, 티켓), `추정`(계산이나 경험). 작업 시간과 비용은 이 셋 중 하나가 없으면 쓰지 않고 `확인 필요`로 둔다.
- **"영향 없음"은 근거가 있을 때만.** 확인한 범위와 방법을 함께 쓴다. "영향 없을 것으로 보임"은 추정이고 추정이라고 쓴다.
- **절차는 확인 항목이 붙은 단위로.** 각 단계는 끝났음을 확인하는 명령이나 관측값을 가진다. 확인 없이 다음 단계로 가는 절차는 절차가 아니다. 단계마다 다시 실행해도 안전한지(멱등) 표시한다.
- **되돌릴 수 없는 지점을 숨기지 않는다.** 데이터 마이그레이션, DNS 전환, 삭제처럼 롤백이 안 되거나 비용이 큰 단계는 절차와 롤백 절 양쪽에 표시한다.
- **문장 규칙은 `akbun-writing`의 문장 두 절을 따른다.** 행위자 명시, 한 문장 한 생각, 조건은 지시 앞에, 한 대상 한 이름, 절차에 "간단히·쉽게" 금지.

## 입력 확인

먼저 넘겨받은 자료를 표로 만든다. 없는 것을 추측으로 채우지 않는다.

| 항목 | 있음/없음 | 출처 |
|---|---|---|
| 변경 내용(전→후) | | |
| 스테이징 검증 결과(무엇을 어떻게 확인했나) | | |
| 스테이징 작업 소요 시간 | | |
| 영향 받는 서비스·팀 목록 | | |
| 비용 견적 또는 단가 | | |
| 작업 창(날짜·시간대) | | |
| 롤백 방법과 소요 시간 | | |

없음이 셋 이상이면 인터뷰 질문 목록을 먼저 보이고 답을 받은 뒤 쓴다.

## 문서 구조

아래 순서를 지킨다. 내용이 없는 절은 헤더째 지우지 않고 `확인 필요`를 쓴다. 공지는 빠진 절이 곧 질문이 되는 문서라서 빈 절이 보여야 한다.

1. **한 줄 요약.** 무엇을, 언제, 개발자에게 무엇이 달라지는지 한 문장. 서비스 중단이 있으면 여기서 말한다.
2. **개발자에게 미치는 영향.** 표로. 중단 여부와 시간(측정/추정), 바뀌는 엔드포인트·설정값·환경 변수·권한·도메인, 배포 가능 여부(작업 창 동안 배포 금지인지), 개발자가 해야 할 일 체크리스트(기한 포함), 하지 않아도 되는 것. 영향 없는 서비스도 "확인한 범위"와 함께 적는다.
3. **왜 하나.** 지금 문제나 제약, 그 근거(장애 번호, 모니터링 수치, 비용 추세, 지원 종료 일정). 한두 문단.
4. **무엇을 바꾸나.** 변경 전 → 후. 구성요소 3개 이상이 얽히면 mermaid 다이어그램 하나. 개발자가 몰라도 되는 내부 세부는 링크로 뺀다.
5. **기대 효과.** 수치로. 무엇이 얼마나 좋아지는지, 어느 지표로 언제 확인하는지. 스테이징 측정값이 있으면 그 값과 운영 환산 근거.
6. **작업 절차.** 번호 목록. 각 단계에 담당, 예상 시간, 확인 방법(명령 또는 관측값), 멱등 여부, 되돌릴 수 없는 단계 표시.
7. **작업 시간과 일정.** 작업 창, 총 예상 시간과 근거(스테이징 실측 × 운영 배수 등), 지연 시 판단 기준(몇 분 넘으면 롤백 결정).
8. **롤백.** 롤백을 결정하는 조건(관측값과 임계값), 절차, 소요 시간, 롤백 뒤 상태(데이터 손실 여부), 롤백이 불가능해지는 지점과 그 시점 이후의 대안.
9. **비용.** 월 증가액과 계산식(단가 × 수량, 단가 출처), 일회성 비용, 절감분이 있으면 순증. 견적이 없으면 `확인 필요`.
10. **리스크와 완화.** 변경 범위 밖에서 깨질 수 있는 것(의존 서비스, 배치, 외부 연동, 캐시·DNS TTL), 각 리스크의 확인 방법과 완화책. 가능하면 `akbun-analysis-gitdiff-blast-radius`의 결과를 여기 붙인다.
11. **스테이징 검증 결과.** 무엇을 어떤 방법으로 확인했고 결과가 무엇이었는지, 증거 위치(대시보드, 로그, PR). 검증하지 않은 것도 적는다.
12. **작업 중 소통.** 담당자, 상태를 공유하는 채널, 작업 시작·완료·롤백 시 알림 방식, 문제 발견 시 연락 경로.
13. **확인 필요.** 문서 안의 `확인 필요`를 모아 누가 언제까지 답할지.

## 쓰지 않는 것

- 근거 없는 "영향 없음", "안전함", "문제 없을 것"
- 개발자에게 무관한 인프라 내부 구현 세부
- 확인 방법이 없는 절차 단계
- 스테이징에서 측정하지 않은 시간을 측정한 것처럼 쓰는 것
- `완벽`, `안정적으로`, `원활하게` 같은 수식. 대신 수치와 조건
- 특정인 비난, 과거 장애의 책임 서술

## 산출물

- 파일로 저장한다. 사용자가 경로를 정하지 않으면 현재 디렉터리에 `YYYY-MM-DD-<작업명>-운영작업공지.md`. 존재하면 덮어쓰기 전에 한 줄 확인.
- 저장 뒤 `akbun-writing-naturalize`의 규칙 파일(`references/common-rules.jsonl`, `references/user-rules.jsonl`)과 처리 절차(맞춤법 교정 → 국소 자연화 → 원문 대조)를 호출 모드로 적용해 원본에 덮어쓴다. 표의 값, 수치·시간·비용, 명령, 도메인·경로, `확인 필요` 표시, 측정/인용/추정 라벨은 보호 영역이다.
- 대화창에는 파일 경로, `확인 필요` 목록(누구에게 물을지), 되돌릴 수 없는 단계 목록만 보고한다.

## 점검표

1. 첫 화면만 읽은 개발자가 "내 서비스에 뭐가 달라지고 내가 뭘 해야 하나"를 아는가.
2. 시간·비용·효과 수치마다 측정/인용/추정 라벨과 출처가 있는가.
3. 절차의 모든 단계에 확인 방법이 있는가. 되돌릴 수 없는 단계가 절차와 롤백 양쪽에 표시돼 있는가.
4. 롤백 결정 조건이 관측값과 임계값으로 적혀 있는가.
5. "영향 없음"마다 확인한 범위가 붙어 있는가.
6. 스테이징에서 검증하지 않은 것이 검증한 것처럼 읽히지 않는가.
7. `확인 필요`가 13절에 모여 있고 답할 사람이 있는가.
