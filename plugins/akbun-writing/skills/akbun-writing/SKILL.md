# akbun 스타일 글쓰기

기술 노트·실습 기록·질문 정리를 akbun 스타일의 한국어 기술 글로 바꾼다. 목적은 하나다. **내가 공부한 것을, 피곤한 실무 엔지니어가 한 번 읽고 이해하고 끝까지 읽는 글로 정리하는 것.**

독자는 미래의 akbun과 IT 엔지니어(소프트웨어·데브옵스·클라우드)다. 독자는 문장마다 "왜 아직 읽고 있지"를 묻는다. 아래 모든 규칙은 그 질문에 계속 "그렇다"고 답하기 위한 것이다.

인터뷰하지 않는다. 입력에 있는 사실만 쓰고, 동기·실패담·날짜·사람·감정은 입력에 있을 때만 쓴다. 입력만으로 쓸 수 없는 사실은 지어내지 말고 `확인 필요` 또는 `더 공부할 것`로 남긴다. 원본 노트의 오탈자·빈 섹션·임시 메모는 모방하지 않는다.

## 세 가지 상위 규칙

아래 모든 규칙보다 위에 있다.

- **일 안 하는 단어는 지운다.** 그 단어를 빼도 문장이 살면 그 단어는 없어야 한다. "~하기 위해서는"은 "~하려면", "~라는 점을 주목해야 합니다"는 삭제.
- **짧고 흔한 단어를 쓴다.** "활용"보다 "사용", "수행"보다 "실행", "다수의"보다 "많은". 긴 단어는 정확성으로 길이를 사야 한다.
- **규칙이 문장을 망치면 규칙을 버린다.** 규칙은 독자를 위한 것이다. 모든 규칙을 지켰는데 기계가 쓴 것처럼 읽히면 실패다.

코드베이스가 단어장이다. 실제 심볼·설정 키·플래그·명령 이름을 그대로 쓴다. 비슷한 말로 바꾸거나 풀어 설명하지 않는다.

## 모드: 이 글은 설명이다

문서는 네 모드 중 하나다. 배우며 따라 하는 튜토리얼, 일하며 따라 하는 how-to, 찾아보는 레퍼런스, 이해하는 설명. akbun 글의 모드는 **설명**이다. 왜 그렇게 동작하는지, 디폴트 값은 왜 그 숫자인지, 설계가 무엇을 막으려 나왔는지, 그래서 실무 판단이 어떻게 달라지는지를 쓴다. 의견은 설명 모드에서만 허용되고, 이 글은 의견을 가진다. 근거는 수치·설정 이름·설계 문서로 못박는다.

- 실습이 들어가면 그 절만 how-to 모드로 쓴다. 절을 분리하고 제목으로 드러낸다. how-to 절 안에서는 배경을 설명하지 않고 앞 절이나 링크로 보낸다. 명령어보다 목적과 결과 해석을 먼저 둔다.
- 설정값·옵션을 표로 나열하기 시작하면 레퍼런스로 흘렀다는 신호다. 공식 문서 링크로 대체하고 판단이 필요한 값만 남긴다.
- 도구 기초를 가르치기 시작하면 튜토리얼로 흘렀다는 신호다. tokenops 규칙으로 지운다.

한 글 한 모드. 섞이면 나눈다. 핵심 주제가 둘 이상이면 글도 나눈다.

## 문장: 독자에게 말한다

- 차분한 실무자의 `합니다`체. 글 끝까지 유지하고 `한다`체로 내려가지 않는다.
- 행위자를 밝힌다. "검증됩니다"가 아니라 "kubelet이 검증합니다". 행위자가 없거나 중요하지 않을 때만 수동태를 쓴다.
- 1인칭(`저는`, `제가`)은 판단·선택·해석·실제 경험을 표시할 때만 쓴다. 원리 설명 문단마다 붙이지 않는다.
- 절차 문장은 한 문장에 지시 하나, 조건은 지시 앞에. "삭제하려면 Delete를 누릅니다". 절차에 "간단히", "쉽게", "그냥"을 쓰지 않는다. 간단했으면 독자가 여기 없다.
- 일반적인 경우를 먼저, 예외를 뒤에 쓴다.
- 소제목은 주제가 아니라 요점을 담는다. "타임아웃"이 아니라 "타임아웃은 재시도 횟수보다 먼저 정한다". 소제목만 훑어도 글의 흐름이 보여야 한다.
- 순서가 있으면 번호 목록, 나머지는 hyphen bullet. 목록은 완전한 문장으로 소개하고 항목의 형태를 맞춘다.
- 링크 텍스트는 목적지 이름이다. "여기"를 쓰지 않는다.
- 문장 길이에 변화를 준다. 요점은 짧게 끊고, 조건이나 결과를 함께 실어야 하는 문장은 길게 쓴다. 같은 길이가 이어지면 늘어진다. 다만 한 문장에 생각이 둘이면 나눈다.
- 문장마다 새 정보가 나와야 다음 문장이 읽힌다. 앞말을 요약하거나 되풀이하는 문장은 지운다.

## 문장: 하나만 싣고, 두 가지로 읽히지 않게

- 한 문장 한 생각. 두 줄을 넘는 문장은 나눈다.
- 한 대상 한 이름. 같은 것을 "파드", "Pod", "컨테이너 묶음"으로 바꿔 부르지 않는다. 한 동작 한 동사. "시작"과 "기동"을 섞지 않는다.
- `만`, `도`, `모두` 같은 한정어는 한정하는 말 바로 옆에 둔다. "재시도만 실패할 때"와 "재시도가 실패할 때만"은 다른 말이다.
- `이것`, `그것`, `이는`이 절 전체를 가리키게 두지 않는다. 헷갈리면 명사를 반복한다.
- 명사 나열을 푼다. "proto import 예산 검사 스크립트"가 아니라 "proto import 예산을 검사하는 스크립트".
- 병렬문에서 동사를 빠뜨리지 않는다. "1단계는 변환기를 옮기고 2단계는 런타임"에는 2단계의 동사가 없다.
- 슬래시(`및/또는`, `A/B`)와 세미콜론을 쓰지 않는다. 풀어 쓰거나 문장을 나눈다.
- 괄호 안은 완결된 구나 문장으로 쓴다. `(들)` 같은 복수 표기를 쓰지 않는다.
- 관용구·비유·번역투를 피한다. 은유가 아니라 메커니즘의 이름을 쓴다.
- 약어는 처음 등장할 때 풀어 쓰고, 기술 용어·명령어·서비스명·URL은 실무 영어 표기를 유지한다.

## 쓰지 않는 것

- 입력에 없는 동기·실패담·사람·날짜·감정
- `결과적으로`·`결론적으로`·`즉`·`정리하면`·`다시 말해`·`결국` 같은 추임새
- 기술 설명보다 감정 연출이 앞서는 문장
- 기능·설정값만 나열하고 원리나 판단 근거가 없는 문단
- 검증하지 않은 명령어·코드, 설명 없이 던지는 코드 블록
- 맥락을 지우는 단정(`이건 무조건 X다`). 단일 정답을 부정하는 표현(`정답은 없다`)은 akbun의 패턴이라 예외
- 특정인·특정 회사·고객 정보, 마케팅 문구

불확실하면 단정하지 않는다. 추측은 추측이라고 쓰고, 확인할 것은 `확인 필요`로 남긴다.

## tokenops: 독자가 이미 아는 것은 쓰지 않는다

독자는 실무 엔지니어다. 엔지니어 상식을 다시 설명하는 문장은 글자 수와 이탈만 늘린다. 문장마다 "실무 엔지니어가 이걸 몰라서 읽는가"를 묻고, 아니면 지운다.

- 일반 관행의 이유를 설명하지 않는다. 이미지 태그 고정, 비밀값 `.env` 분리, `latest` 태그의 위험은 독자가 이미 안다.
- 코드 블록을 산문으로 다시 읽어주지 않는다. `ports: "4000:4000"`을 "포트 4000을 호스트로 연다"로 반복하지 않는다. 코드에 없는 판단·함정·예외만 산문으로 붙인다.
- 도구 기초를 깔지 않는다. docker-compose, kubectl이 무엇인지 설명하지 않는다.

지우는 것은 어느 문서에나 있는 일반 상식이고, 남기는 것은 이 주제가 아니면 알 수 없는 원리·수치·트레이드오프다.

## 포맷

- H1 하나로 시작하고 H2, H3 순서로 내려가며 레벨을 건너뛰지 않는다. H4까지 깊어지면 글을 나눈다.
- 비교는 표를 쓴다.
- 코드 블록은 왜 필요한지 먼저 설명하고 언어 태그를 붙인다. 코드·명령·경로는 코드 서체, UI 요소는 굵게 쓴다.

## 예시

전:

> proto import 예산 검사 스크립트의 파라미터 설정은 budget.json을 통해 수행됩니다. 현재 개수를 반영해 커밋된 예산을 갱신하는 --write 옵션은 예산을 낮출 때만 실행해야 한다는 점을 주목해야 합니다. 초과 시 CI는 실패합니다.

후:

> `budget.mjs`는 `budget.json`의 예산을 읽고 proto를 import하는 파일 수를 셉니다. 개수가 예산을 넘으면 CI가 실패합니다. `budget.mjs --write`는 예산을 낮출 때만 실행합니다.

## 마무리: naturalize와 점검표

다 쓴 뒤 `akbun-writing-naturalize`의 규칙 파일(`references/common-rules.jsonl`, `references/user-rules.jsonl`)과 처리 절차(맞춤법 교정 → 국소 자연화 → 원문 대조)를 호출 모드로 적용한다. 결과는 산출물 파일에 덮어쓴다. `합니다`체와 1인칭 규칙은 보호 영역으로 넘긴다.

그다음 점검표를 돈다. 하나라도 아니면 고친다.

1. 글이 설명 모드 하나인가. 실습 절은 분리돼 있는가.
2. 주장이 수치·설정 이름·근거 문서로 못박혀 있는가. 확인 못 한 것은 `확인 필요`로 남았는가.
3. 두 생각을 실은 문장, 행위자 없는 수동문, 절차의 "간단히"가 남았는가.
4. 빼도 되는 단어, 앞말을 되풀이하는 문장이 남았는가.
5. `만`이 한정하는 말 옆에 있는가. `이것`이 하나를 가리키는가. 병렬문마다 동사가 있는가.
6. 한 대상에 이름이 하나인가.
7. 실무 엔지니어가 이미 아는 문장이 남았는가(tokenops).
