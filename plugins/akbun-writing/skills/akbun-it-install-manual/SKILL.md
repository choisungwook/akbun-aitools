# IT 시스템 설치 매뉴얼

이 제품을 처음 접하는 사람이 매뉴얼을 위에서 아래로 따라 하기만 하면 설치가 끝나도록 쓴다. 정확하고 완전한 레퍼런스가 아니라, 부담 없이 한 번 해 보게 만드는 문서다. 설명은 최소로 줄이고, 독자가 명령을 실행하면서 스스로 깨닫게 한다.

## 원칙

- **설명은 짧게, 단계는 빠짐없이.** 배경 설명은 한두 줄이면 충분하다. 반면 설치 단계는 하나도 건너뛰지 않는다. 분량 제한은 단계에 적용하지 않는다.
- **한 단계 = 설명 1~2줄 + 코드 블록 1개.** 독자는 설명을 읽고 코드 블록을 그대로 복사해 실행한다. 한 단계에서 여러 일을 시키지 않는다. 명령이 두 종류면 단계를 나눈다.
- **비밀값은 `XXX`로 마스킹.** 비밀번호, 토큰, API key, 접속 문자열의 비밀 부분은 코드 블록 안에서 `XXX`로 쓴다. 예: `--password XXX`, `token: XXX`. 마스킹한 값이 있으면 바로 아래 한 줄로 무엇을 넣어야 하는지 알려 준다.
- **독자 눈높이는 입문자.** 제품을 오늘 처음 들어 본 사람이 읽는다. 기술 용어는 처음 나올 때 한 줄로 설명한다. 알아야 할 개념이 많아도 설치에 필요한 것만 남긴다.
- **결과를 보여 준다.** 명령 실행 뒤 화면에 무엇이 보여야 정상인지 짧게 적는다. 독자가 "이게 맞나?" 하고 멈추지 않게 한다.
- **실제 확인한 것만 쓴다.** 제품 공식 문서, 사용자가 준 자료, 실제 실행 결과에서 확인한 명령과 경로만 쓴다. 기억에 의존해 옵션을 만들어 내지 않는다. 확인하지 못한 값은 `확인 필요`로 표시한다.

## 재료 모으기

1. 설치 대상 제품·버전, 설치 환경(OS, Kubernetes, 클라우드 등), 설치 방식(패키지, 컨테이너, Helm, 바이너리 등)을 사용자에게 확인한다. 사용자가 말하지 않은 것은 공식 문서의 기본 방식을 따르고, 그 선택을 문서 첫 부분에 한 줄로 밝힌다.
2. 제품 공식 문서와 사용자가 제공한 자료(설치 기록, 스크립트, 설정 파일, 스크린샷)를 근거로 삼는다. 자료가 있으면 그 자료를 우선한다.
3. 사전 준비 항목(방화벽 포트, IP·도메인, 계정·권한, 필요한 도구, 최소 사양)은 공식 문서의 요구 사항에서 뽑고, 사용자 환경에 맞춰 조정한다.
4. 자료에서 확인할 수 없는 내용은 사용자에게 한 번에 묻는다. 추정해서 채우지 않는다.

## 문서 구조

7개 장을 이 순서로 쓴다. 장 제목은 독자가 쓰는 말로 바꿔도 되지만 순서는 바꾸지 않는다.

| 장 | 내용 | 분량 |
|---|---|---|
| 1. 이 제품은 | 제품이 무엇이고 왜 쓰는지 | 1~2줄 |
| 2. 구조 | 아키텍처 구조와 네트워크 구조 Mermaid | 그림 1~2장 + 각 1~3줄 |
| 3. 사전 준비 | 설치 전에 갖춰야 할 것 | 체크리스트 표 1 |
| 4. 주의 사항 | 꼭 확인해야 하는 것, 실수하면 되돌리기 어려운 것 | 3~7개 항목 |
| 5. 설치 | 번호 순서 단계 | 단계 수 제한 없음 |
| 6. 설치 확인 | 제대로 설치됐는지 보는 방법 | 단계 1~3개 |
| 7. 클린업 | 설치한 것을 지우는 방법 | 단계 수 제한 없음 |

## 장별 내용

- **1. 이 제품은:** 제품이 무슨 일을 하는지, 이 매뉴얼로 어떤 상태까지 만드는지(예: "단일 노드에 설치하고 웹 UI 접속까지")를 1~2줄로 쓴다. 역사, 경쟁 제품 비교, 기능 나열은 넣지 않는다.
- **2. 구조:** Mermaid 두 장을 그린다. 아키텍처 구조는 이 매뉴얼로 설치되는 구성 요소와 그 관계를, 네트워크 구조는 어떤 포트로 누가 누구에게 접속하는지를 그린다. 구성이 단순해 한 장으로 둘 다 표현되면 한 장만 그린다. 그림마다 위에 무엇을 그린 것인지 한 줄 쓰고, 아래에 설치하면서 마주칠 구성 요소 이름을 1~3줄로 설명한다. 이 매뉴얼로 설치하지 않는 구성 요소는 그리지 않는다.
- **3. 사전 준비:** `항목 | 필요한 것 | 확인 방법` 표로 쓴다. 항목은 최소 사양(CPU·메모리·디스크), OS·런타임 버전, 필요한 도구(예: kubectl, Helm, Docker), 네트워크(열어야 할 방화벽 포트·방향, 고정 IP·도메인), 계정·권한(sudo, 클라우드 IAM, 외부 서비스 계정), 미리 받아 둘 값(라이선스 키, 인증서)을 기본 후보로 두고 제품에 맞게 넣고 뺀다. 확인 방법에는 독자가 실행해 볼 명령을 짧게 쓴다. 이 표에 없는 것을 5장에서 갑자기 요구하지 않는다.
- **4. 주의 사항:** 설치 전에 반드시 알아야 할 것을 항목으로 쓴다. 한 번 정하면 바꾸기 어려운 값(설치 경로, DB 이름, 도메인), 데이터가 지워지는 명령, 버전 호환성, 운영 환경에서 기본값을 그대로 쓰면 안 되는 설정(기본 비밀번호, 외부 노출 포트)이 기본 후보다. 각 항목은 "무엇을 + 왜"를 1~2줄로 쓴다. 겁주는 문장이 아니라 확인 항목으로 쓴다.
- **5. 설치:** `### 1.`, `### 2.` 같은 번호 소제목으로 단계를 나눈다. 각 단계는 설명 1~2줄, 코드 블록 1개, 필요하면 "이렇게 보이면 정상" 1줄 순서로 쓴다. 설정 파일을 만드는 단계는 파일 전체를 코드 블록으로 주고, 독자가 바꿔야 하는 값은 `XXX`나 `<자기-값>`으로 표시한 뒤 아래에 무엇을 넣는지 적는다. 실행 위치(디렉터리)나 실행 계정이 바뀌면 그 단계에 밝힌다. 단계 사이에 기다려야 하는 시간이 있으면 적는다.
- **6. 설치 확인:** 설치가 끝났음을 독자가 눈으로 확인하는 단계다. 상태 조회 명령과 기대 출력, 웹 UI가 있으면 접속 주소와 첫 화면, 간단한 동작 시험(예: 요청 하나 보내기)을 5장과 같은 형식으로 쓴다. 실패했을 때 가장 흔한 원인 1~3개를 `증상 | 원인 | 확인 명령` 표로 덧붙인다.
- **7. 클린업:** 이 매뉴얼로 만든 것을 모두 지우는 단계를 5장과 같은 형식으로 쓴다. 설치의 역순으로 지운다. 데이터가 함께 지워지는 명령에는 바로 위에 한 줄로 경고한다. 3장에서 독자가 만든 것(방화벽 규칙, 계정)도 지우는 대상에 넣는다. 클린업이 끝난 상태를 확인하는 명령을 마지막에 둔다.

## 코드 블록 규칙

- 모든 코드 블록에 언어를 표시한다(`bash`, `yaml`, `ini`, `sql` 등).
- 코드 블록 위에는 반드시 그 코드가 무엇인지 설명하는 문장을 둔다.
- 셸 명령에는 프롬프트 기호(`$`, `#`)를 붙이지 않는다. 독자가 그대로 복사해 붙여 넣는다.
- 여러 줄 명령은 한 블록에 두되 각 줄이 하나의 일을 하게 한다.
- 출력 예시는 명령 블록과 분리해 `text` 블록으로 둔다.
- 비밀값 마스킹은 `XXX`로 통일한다. 예시 값이라도 실제 형태의 비밀번호·토큰을 쓰지 않는다.

## 톤

- 1장은 `합니다`체로, 나머지는 짧은 개조식으로 쓴다.
- 제품명, 명령어, 옵션은 원문 영어 표기를 유지한다.
- "쉽습니다", "간단합니다" 같은 평가를 넣지 않는다. 독자에게는 쉽지 않을 수 있다.
- 한 단계에서 여러 선택지를 주지 않는다. 기본 경로 하나만 안내하고, 대안은 문서 끝에 한 줄로만 언급한다.

## 완료 전 확인

- 제품 소개가 2줄을 넘지 않는가?
- Mermaid에 그린 구성 요소가 모두 5장에서 실제로 설치되는가?
- 5장에서 요구하는 것이 3장 사전 준비 표에 빠짐없이 있는가?
- 모든 단계가 설명 1~2줄 + 코드 블록 1개 형식인가? 한 단계에 명령 두 종류가 섞이지 않았는가?
- 코드 블록 안 비밀번호·토큰·키가 모두 `XXX`인가?
- 각 명령의 실행 위치·계정이 바뀌는 지점을 밝혔는가?
- 설치 확인 장에 기대 출력이 있는가?
- 클린업이 설치의 역순이고, 3장에서 만든 것까지 지우는가?
- 데이터가 지워지는 명령 위에 경고가 있는가?
- 확인하지 못한 명령·값을 사실처럼 쓰지 않았는가?
