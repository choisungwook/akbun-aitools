# IT 시스템 온보딩 문서

이 skill은 코드베이스와 사용자의 설명을 받아, **맥락이 전혀 없는 사람이 첫날에 한 번 읽는 온보딩 문서**를 Markdown 한 장으로 만든다.

기준은 하나다. 코드를 읽으면 언젠가 알게 되는 것은 이 문서의 몫이 아니다. 컴포넌트 관계도, API 목록, 파일 구조는 신입도 결국 도달한다. 코드를 아무리 읽어도 안 나오는 것은 세 가지다. **이 시스템이 왜 존재하는가, 회의에서 쓰는 말이 코드의 무엇인가, 왜 이렇게 생겼는가.** 분량은 이 셋에 몰아준다.

## 재료 모으기

1. **코드에서 채운다.** 시스템 지도, 대표 시나리오의 코드 경로, 실행 방법, 배포 설정은 repo에서 확인한다.
2. **`akbun-analysiscode` 산출물이 있으면 재분석하지 않는다.** 경로를 안 받았으면 `$AKBUN_ANALYSIS_HOME`(기본값 macOS `~/Library/Application Support/akbun-analysis`, Windows `%APPDATA%/akbun-analysis`, Linux `${XDG_DATA_HOME:-~/.local/share}/akbun-analysis`)의 `projects.json`에서 이 repo의 `analysis.json`을 찾는다. 찾으면 시스템 지도는 요약 + HTML 링크로 끝낸다. **없거나 어느 프로젝트인지 애매하면 사용자에게 묻는다.** 짐작으로 다른 프로젝트 분석을 가져다 쓰지 않는다.
3. **코드에 없는 것만 사용자에게 묻는다.** 도메인 용어의 실제 의미, 업무 흐름, 자주 나는 장애, 설계 이유, 물어볼 사람. 한 번에 모아서 묻는다.
4. **그래도 모르면 `확인 필요`로 남긴다.** 온보딩 문서는 반드시 썩는다. 빈칸 표시가 틀린 문장보다 낫다.

코드와 사용자 설명이 다르면 충돌을 문서에 적고 코드 기준 해석을 제시한다.

## 문서 구조와 분량

15분 안에 1회독되는 분량으로 쓴다.

| 단 | 섹션 | 분량 |
|---|---|---|
| 1부 | 이 시스템은 무엇인가 (한 문단 요약) | 300~400자 |
| 1부 | 누가 왜 쓰나 (연관 부서·장애 시 연락처 포함) | 500~700자 |
| 1부 | 도메인 용어 사전 | 표, 8~15행 |
| 1부 | 시스템 지도 | 600~800자 + 다이어그램 1 |
| 2부 | 대표 시나리오 관통 | 800~1,200자 |
| 2부 | 코드 지도와 첫 실행 | 500~800자 |
| 2부 | 운영 현실 | 600~900자 |
| 2부 | 함정과 암묵지 | 400~700자 |
| 2부 | 첫 과제와 물어볼 사람 | 200~400자 |

1부는 개발자가 아닌 동료(기획·운영·CS)도 읽고 2부는 개발자만 읽는다. 문서 첫머리에 이 경계를 한 줄로 알린다.

## 1부: 이 시스템은 무엇인가

기술 스택 나열로 시작하지 않는다. 읽는 사람은 아직 이 시스템에 관심이 없다. 기술 용어는 처음 나올 때 한 줄로 풀어준다.

- **한 문단 요약.** 두 질문에 이 순서로 답한다. 첫째, **고객에게 무엇을 제공하는가.** 내부 처리 과정이 아니라 고객이 손에 쥐는 결과로 쓴다. 둘째, **오늘 멈추면 누구의 무슨 일이 멈추는가.** 앞이 존재 이유를 세우고 뒤가 그 크기를 증명한다.
- **누가 왜 쓰나.** 사용자 유형과 그들의 실제 업무 흐름 한두 개. 조직도가 아니라 일의 흐름이다. 여기에 두 가지를 반드시 넣는다. 첫째, **연관 부서** — 이 시스템 앞뒤에 붙어 데이터를 넣거나 받아가는 부서·시스템과, 각각 무엇을 주고받는지. 둘째, **장애 시 연락 부서** — 이 시스템이 멈추면 어디에 알려야 하고 어디서 연락이 오는지를 표로 남긴다. 팀에 새로 들어온 사람이 첫 장애에서 가장 먼저 막히는 지점이다.
- **도메인 용어 사전.** 열은 `용어 | 뜻 | 코드·DB에서의 이름`이다. **회의에서 쓰는 말과 코드 식별자를 같은 행에 두는 것이 이 표의 전부다.** 회의의 "정산"이 `settlement`인지 `payout`인지 못 이으면 몇 주를 헤맨다. 시스템 밖에서 다른 뜻으로 쓰이는 말은 그 차이를 적는다.
- **시스템 지도.** 컴포넌트를 5~9개로 묶는다. 그 이상은 첫날에 못 외운다. mermaid 한 장과 컴포넌트별 한 줄 역할 표를 둔다. 외부 의존(결제사, 사내 인증, 큐)은 빠뜨리지 않는다. 장애의 절반이 거기서 온다.

## 2부: 코드로 들어가기

여기부터 독자는 개발자다. `docker`나 `kubectl`이 무엇인지 설명하지 않고, 코드 블록을 산문으로 다시 읽어주지 않는다. 이 시스템이 아니면 알 수 없는 것만 쓴다.

- **대표 시나리오 관통.** 이 문서의 심장이다. 가장 흔한 요청 하나를 골라 진입점부터 응답까지 `file:line`으로 따라간다. 단계마다 "여기서 무엇이 자주 터지는가"를 한 줄 붙인다. 시나리오는 하나면 된다. 둘째를 넣고 싶으면 대신 첫째를 더 깊게 판다.
- **코드 지도와 첫 실행.** 디렉터리를 전수 나열하지 않는다. 자주 건드리는 곳과 손대면 안 되는 곳만 표로 남기고 **처음 읽을 파일 3개**를 지정한다. 실행 명령에는 성공 판정(무엇이 뜨면 된 것인가)을 반드시 붙인다. 판정 없는 절차는 읽는 사람을 막다른 길에 세운다.
- **운영 현실.** 배포 경로, 로그·대시보드 위치, 자주 나는 장애 세 가지와 첫 대응, 알림이 오는 곳. 팀에 새로 들어온 사람이 가장 늦게 배우고 가장 먼저 필요한 영역이다.
- **함정과 암묵지.** 왜 이렇게 생겼는지, 이름과 실제 동작이 다른 곳, 고치고 싶어 보이지만 건드리면 안 되는 곳, 알려진 부채. 역사는 사용자에게 들은 것만 쓴다. 그럴듯한 사연을 지어내지 않는다.
- **첫 과제와 물어볼 사람.** 첫 주에 해볼 작은 변경 한두 개, 영역별 담당, 그리고 이 문서의 `확인 필요` 목록.

## 톤

- **개조식으로 쓴다.** 온보딩 문서는 정독하는 글이 아니라 필요할 때 찾아보는 문서다. 항목을 짧게 끊고 명사형이나 `~함`으로 맺어, 한 항목이 한 줄에 들어오게 한다. 줄글로 늘어놓지 않는다.
- 예외는 1부의 **한 문단 요약**뿐이다. 여기만 차분한 존댓말(`합니다`체) 서술형으로 쓴다. 읽는 이유를 만드는 문단이라 개조식으로는 설득되지 않는다.
- 기술 용어·명령어·서비스명은 실무 영어 표기를 유지하고, 약어는 처음 등장할 때 풀어 쓴다.
- 확실하지 않은 것은 단정하지 않는다. 추측은 추측이라고 쓴다.
- 조직도·인사 정보·특정인 평가는 넣지 않는다.

## 완료 전 확인

1. 맥락이 없는 엔지니어가 이 문서만 보고 로컬에서 첫 요청을 성공시킬 수 있는가.
2. 대표 시나리오를 에디터에서 코드로 따라갈 수 있는가.
3. 회의에서 들은 도메인 용어를 코드 식별자로 연결할 수 있는가.
4. 확인하지 못한 것을 아는 것처럼 쓰지 않았는가.
