# IT 시스템 온보딩 문서

직무와 관계없이 이 서비스를 처음 접하는 사람이 전체 모습을 이해하도록 쓴다.

서비스를 이해하는 데 필요한 내용에 집중한다.

1. 시스템이 왜 존재하는가.
2. 업무 용어가 실제 흐름에서 무엇을 뜻하는가.
3. 어떤 외부 시스템에 의존하고 어디에서 실행되는가.
4. 어떻게 배포하며 무엇을 주의해야 하는가.

API·파일·컴포넌트 전수 목록은 온보딩 문서에 옮기지 않는다. `akbun-analysiscode` 산출물은 시스템 지도와 외부 의존성을 요약하는 근거로만 쓴다.

## 재료 모으기

1. 시스템 구성, 외부 연동, 인프라, 배포 방식은 사용자가 제공한 코드와 문서에서 확인한다.
2. `akbun-analysiscode` 산출물이 있으면 구조를 다시 분석하지 않는다. 경로가 없으면 `$AKBUN_ANALYSIS_HOME`의 `projects.json`에서 현재 repo의 `analysis.json`을 찾는다.
   - 기본 경로: macOS `~/Library/Application Support/akbun-analysis`, Windows `%APPDATA%/akbun-analysis`, Linux `${XDG_DATA_HOME:-~/.local/share}/akbun-analysis`
   - 찾으면 시스템 지도는 요약과 HTML 링크만 제공한다.
   - 프로젝트가 불명확하면 사용자에게 묻고, 다른 프로젝트 결과를 추정해 쓰지 않는다.
3. 연관 부서는 코드·문서에서 추정하지 않는다. 사용자 인터뷰로 부서명, 역할, 주고받는 정보, 협업 시점, 장애 연락 부서를 확인한다.
4. 자료에서 확인할 수 없는 도메인 의미, 업무 흐름, 외부 의존성, 인프라, 배포 절차, 주의사항은 사용자에게 한 번에 묻는다. 업무 규칙의 예외, 알려진 제약, 현재 방식이 된 이유도 직접 질문한다. 답변에 빈틈이 있으면 후속 질문하고, 추정해서 채우지 않는다.
5. 확인하지 못한 내용은 `확인 필요`로 표시한다.

코드·문서와 사용자 설명이 충돌하면 차이를 밝힌다. 현재 동작은 코드·문서, 업무 의미는 사용자 설명을 기준으로 쓴다.

## 문서 구조와 분량

15분 안에 1회독되는 분량으로 쓴다.

| 섹션 | 분량 |
|---|---|
| 이 시스템은 무엇인가 (한 문단 요약) | 300~400자 |
| 누가 왜 쓰나 (연관 부서·장애 시 연락처 포함) | 500~700자 |
| 도메인 용어 사전 | 표, 8~15행 |
| 시스템 지도 | 600~800자 + 다이어그램 1 |
| 서비스 이용 흐름 | 800~1,200자 |
| 인프라와 배포 | 600~800자 + 다이어그램 1 |
| 주의할 점과 특이사항 | 400~700자 |

## 서비스 이해

- **한 문단 요약:** 기술 스택 대신 고객이 얻는 결과와 시스템 중단 시 멈추는 일을 차례로 설명한다.
- **누가 왜 쓰나:** 사용자 유형과 실제 업무 흐름 1~2개를 적는다. 인터뷰에서 확인한 연관 부서는 `부서 | 역할 | 주고받는 정보 | 협업 시점` 표로 정리하고, 장애 연락 부서도 명시한다.
- **도메인 용어 사전:** `용어 | 뜻 | 사용되는 업무 단계` 표로 업무 용어와 실제 흐름을 연결한다. 시스템 밖에서 뜻이 다르면 함께 적는다.
- **시스템 지도:** 분석 산출물이 없을 때만 컴포넌트 5~9개를 Mermaid 한 장과 역할 표로 정리한다. 외부 의존성은 `외부 시스템 | 주고받는 정보 | 서비스 영향` 표로 분리한다.

기술 용어는 처음 나올 때 한 줄로 설명한다.

## 서비스 흐름

- **서비스 이용 흐름:** 대표적인 고객 행동이나 업무 하나를 시작부터 결과까지 설명한다. 담당 역할, 오가는 정보, 거치는 시스템, 주요 실패 지점만 적고 API·파일 호출 순서는 다루지 않는다.

## 인프라와 배포

- **인프라 구조:** AWS 같은 cloud, EKS 같은 실행 환경, network 경계, 주요 저장소와 queue를 Mermaid 한 장으로 정리한다. 확인된 제품명과 구성만 쓴다.
- **배포 방법:** 배포 시작 조건, 실행 순서, 완료 확인, 실패 시 되돌리는 방법을 적는다.
- **주의할 점과 특이사항:** 사용자 인터뷰로 업무 규칙의 예외, 알려진 제약, 현재 방식이 된 이유, 배포 전 준비, 작업 순서, network 순단, 점검 시간, 수동 작업을 최대한 확인한다. 확인된 내용만 쓴다.

## 톤

- 한 문단 요약만 `합니다`체로 쓰고, 나머지는 짧은 개조식으로 쓴다.
- 기술 용어·서비스명은 실무 영어 표기를 유지하고, 약어는 처음 등장할 때 풀어 쓴다.
- 확실하지 않은 것은 단정하지 않는다. 추측은 추측이라고 쓴다.
- 조직도·인사 정보·특정인 평가는 넣지 않는다.

## 완료 전 확인

- 시스템이 제공하는 가치와 주요 업무 흐름을 설명할 수 있는가?
- 연관 부서의 역할과 협업 시점이 사용자에게 확인되었는가?
- 업무 용어를 실제 업무 단계와 연결할 수 있는가?
- 외부 의존성과 장애 시 영향을 찾을 수 있는가?
- 인프라 구조와 배포 방법을 파악할 수 있는가?
- 주의사항과 특이사항이 사용자에게 확인된 내용인가?
- 미확인 내용을 사실처럼 쓰지 않았는가?
