# IT 시스템 온보딩 문서

직무와 관계없이 이 서비스를 처음 접하는 사람이 전체 모습을 이해하도록 쓴다.

## 재료 모으기

1. 시스템 구성, 연동, 인프라, 배포 방식은 사용자가 제공한 코드와 문서에서 확인한다.
2. 조직·프로세스에 속한 내용은 코드·문서에서 추정하지 않는다. 사용자 인터뷰로 확인한다.
3. 자료에서 확인할 수 없는 내용은 사용자에게 한 번에 묻는다. 답변에 빈틈이 있으면 후속 질문하고, 추정해서 채우지 않는다.
4. 확인하지 못한 내용은 `확인 필요`로 표시한다.

코드·문서와 사용자 설명이 충돌하면 차이를 밝힌다. 현재 동작은 코드·문서, 업무 의미는 사용자 설명을 기준으로 쓴다.

## 문서 구조와 분량

15분 안에 1회독되는 분량으로 쓴다. 아래 8개 섹션을 이 순서로 쓴다.

| 섹션 | 분량 |
|---|---|
| 1. 서비스 개요 | 400~600자 |
| 2. 업무 흐름 | 600~1,000자 |
| 3. 아키텍처 | 400~600자 + 다이어그램 1 |
| 4. 의존성 | 표 2 |
| 5. 인프라 & 배포 | 500~800자 |
| 6. 운영 | 500~800자 |
| 7. 접근 권한 | 표 + 링크 목록 |
| 8. 특이사항 | 400~700자 |

## 섹션별 내용

각 섹션은 아래 질문에 답한다. 답은 이 시스템에서 실제로 확인한 것만 쓰고, 이 skill에 없는 구성 요소나 기술이라도 해당 시스템에 있으면 그대로 쓴다.

- **1. 서비스 개요:** 어떤 고객·사용자의 어떤 문제를 해결하는가. 이 서비스가 없으면 무슨 일이 생기는가(비즈니스 임팩트).
- **2. 업무 흐름:** 사용자 요청부터 처리, 결과까지 이어지는 주요 시나리오 2~3개. 담당 역할, 오가는 정보, 거치는 시스템, 주요 실패 지점만 적고 API·파일 호출 순서는 다루지 않는다. 트래픽 특성(언제 몰리는지, 실시간인지 배치인지)을 덧붙인다.
- **3. 아키텍처:** 이 시스템을 이루는 구성 요소와 그 역할. 요청이 들어와 처리되고 나가기까지 거치는 경로를 Mermaid 한 장으로 그린다. 구성 요소는 시스템마다 다르므로 확인된 것만 넣는다.
- **4. 의존성:** 내부는 `팀 | 시스템 | 호출 방향 | 주고받는 정보`, 외부는 `외부 시스템 | 용도 | 서비스 영향` 표로 나눈다. 각 의존성이 멈췄을 때 장애가 어디까지 번지는지 적는다.
- **5. 인프라 & 배포:** 어디에서 실행되는가(실행 환경, 위치, 계정 구분). 인프라 정의가 어디에 있고, 어떤 절차로 배포하며, 어떻게 되돌리는가. 환경이 여러 개면 환경별 차이를 짚는다.
- **6. 운영:** 상태를 어디에서 보는가(대시보드, 알람 채널), 무엇을 지표로 삼는가(SLI/SLO). 자주 발생하는 장애 유형과 대응법, 온콜 규칙과 escalation 경로.
- **7. 접근 권한:** `필요한 계정·권한 | 용도 | 신청 방법` 표로 정리하고, 저장소·문서·wiki 링크를 목록으로 붙인다.
- **8. 특이사항:** 히스토리에서 온 제약(legacy, 하드코딩, 우회 로직)과 건드리면 안 되는 부분을 이유와 함께 쓴다.

기술 용어는 처음 나올 때 한 줄로 설명한다.

## 톤

- 서비스 개요만 `합니다`체로 쓰고, 나머지는 짧은 개조식으로 쓴다.
- 기술 용어·서비스명은 실무 영어 표기를 유지하고, 약어는 처음 등장할 때 풀어 쓴다.
- 확실하지 않은 것은 단정하지 않는다. 추측은 추측이라고 쓴다.
- 조직도·인사 정보·특정인 평가는 넣지 않는다.

## 완료 전 확인

- 고객이 누구이며 이 서비스가 없으면 무슨 일이 생기는지 설명할 수 있는가?
- 주요 시나리오를 요청부터 결과까지 따라갈 수 있는가?
- 구성 요소와 요청 경로를 파악할 수 있는가?
- 내부·외부 의존성과 장애 전파 범위를 찾을 수 있는가?
- 배포와 되돌리는 방법을 알 수 있는가?
- 알람 채널, 온콜 규칙, escalation 경로가 사용자에게 확인된 내용인가?
- 첫날 필요한 권한을 어떻게 신청하는지 알 수 있는가?
- 이 문서의 모든 구성 요소·기술이 실제 시스템에서 확인된 것인가?
- 미확인 내용을 사실처럼 쓰지 않았는가?
