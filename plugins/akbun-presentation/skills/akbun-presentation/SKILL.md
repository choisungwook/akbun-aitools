# akbun 발표자료 생성

## 이 skill이 하는 일

주제 하나만 받아도, 원본 자료(블로그 글·논문·문서·코드·장애 회고)를 받아도 akbun 스타일 발표
덱으로 만든다. 산출물은 세 가지다.

1. **슬라이드 아웃라인** — 슬라이드별 유형·제목·핵심 메시지를 정리한 표. 생성 전 확인용.
2. **.pptx 파일** — pptxgenjs로 생성한 발표 파일. PowerPoint로 열거나 Google Slides로 가져간다.
3. **발표 대본 .md 파일** — 슬라이드별 상세 대본. 요약본이 아니라 발표자가 그대로 읽고 설명할 수
   있는 완성 원고다.

발표 대본이 이 skill의 절반이다. 슬라이드만 잘 만들고 대본을 슬라이드 요약으로 때우면 실패다.

## 사용자 설정

사용자가 설정을 주면 그대로 따르고, 주지 않은 항목은 아래 기본값을 쓴다. 설정을 물어보느라
작업을 멈추지 않는다. 쓴 값은 작업 시작할 때 한 번 요약해 보여준다.

| 항목 | 기본값 |
|---|---|
| 원본 자료 | 없으면 주제만으로 구성한다 |
| 참고할 기존 PPT | 없음 |
| 발표 시간 | 10분 |
| 목표 슬라이드 수 | 발표 시간 × 1.2~1.5장 (10분이면 12~15장), 상한 30장 |
| 청중 및 난이도 | 배경지식이 부족한 소프트웨어 엔지니어 |
| 발표자의 현재 배경지식 | 이 분야를 처음 접함 |
| 언어 | 슬라이드는 영어, 발표 대본은 한국어 |
| 스타일 | 라이트 샌드위치 (다크 스텝은 요청하거나 참고 PPT가 다크일 때) |

"30장 미만"은 상한이지 목표가 아니다. 10분에 30장이면 슬라이드당 20초라 대본을 읽을 수 없다.
사용자가 슬라이드 수를 직접 지정하지 않았다면 발표 시간에서 계산한 값을 쓰고, 아웃라인에
"10분 / 14장 / 슬라이드당 평균 43초"처럼 근거를 적어 보여준다.

참고 PPT가 주어지면 색·여백·글꼴·전반적인 분위기를 그쪽에 맞추고, 어떤 스타일로 판단했는지
아웃라인에 한 줄 적는다. 배치를 그대로 복사하지는 않는다.

## 작업 순서

1. **design.md 숙지.** [design.md](design.md)에서 색·타이포·레이아웃·그림 언어·말투를 읽는다.
2. **설정 확정.** 위 표대로 설정을 정하고, 원본 자료가 있으면 먼저 끝까지 읽는다.
3. **아웃라인 작성.** 아래 `1. 발표자료 구성` 규칙으로 슬라이드별 유형·제목·핵심 메시지를 표로 만든다.
4. **아웃라인 확인.** 사용자에게 보여주고 진행한다(피드백이 있으면 반영).
5. **대본 먼저 쓴다.** 슬라이드보다 대본을 먼저 쓰면 슬라이드에 뭘 넣고 뭘 빼야 하는지가 정해진다.
   [references/script-template.md](references/script-template.md)를 따른다.
6. **pptx 생성.** [references/pptxgenjs-kit.md](references/pptxgenjs-kit.md)의 검증된 스타일
   키트를 읽고 그대로 복사해 시작한다. 좌표를 잡을 때 라벨·마커가 겹치지 않는지 계산한다.
7. **QA.** 아래 `8. 최종 검수` 목록을 실제로 렌더링해 확인하고, 문제가 있으면 고친 뒤 다시 확인한다.
8. **출력.** 아래 `9. 최종 결과물` 형식으로 답한다.

## 1. 발표자료 구성

- 전체 분량은 확정한 목표 슬라이드 수에 맞춘다.
- 원본 자료가 있으면 그 논리와 전개 순서를 최대한 충실하게 반영한다.
- 기본 전개는 **문제·목적 → 필요한 배경지식 → 핵심 아이디어 → 구체적인 방법·시스템·과정 →
  수식·분석 → 결과와 근거 → 한계와 함의**다. 자료 성격에 맞지 않는 단계는 억지로 넣지 말고
  자연스럽게 조정한다. 논문에는 수식·분석 단계가 있지만 장애 회고에는 없다.
- akbun 스토리 문법은 그대로 유지한다. 정답을 먼저 말하지 않고 **질문 → 여정 → 답** 순서로 간다.
  섹션 사이·반전 지점에 전환(질문) 슬라이드를 끼워 호흡을 조절한다.
- 각 슬라이드는 **핵심 메시지 하나**만 전달한다. 말할 게 두 개면 슬라이드를 나눈다.
- **슬라이드 제목만 순서대로 읽어도 전체 발표의 논리 흐름이 이해돼야 한다.** 아웃라인을 다 쓴 뒤
  제목 열만 세로로 읽어보고, 흐름이 끊기면 제목을 고친다.
- 원본 자료의 중요한 Figure·Chart·Table·Diagram·Algorithm·수식·사례는 빠뜨리지 않는다.
- 발표 시간 안에 설명하기 어려운 부가 내용은 핵심 슬라이드에 욱여넣지 말고 대본이나 부록
  슬라이드로 분리한다.

## 2. 디자인

색·타이포·레이아웃·그림 언어·스크린샷 규칙 등 "결과물이 어떻게 생겼는가"는 모두
[design.md](design.md)에 있다. design.md는 도구에 의존하지 않는 자기완결 스타일 스펙이라 다른
곳에 복붙해 재사용할 수 있고, 그 스펙을 pptxgenjs로 구현한 코드 키트는
[references/pptxgenjs-kit.md](references/pptxgenjs-kit.md)에 있다.

작업 관점에서 특히 지킬 것:

- **레이아웃을 페이지마다 다르게 고른다.** 같은 장식 구성을 기계적으로 반복하지 말고 Figure 중심
  페이지, 수식 중심 페이지, 과정 설명 페이지, 비교 페이지를 내용에 맞게 나눠 쓴다.
- 제목·본문·Figure 사이 간격을 충분히 둔다. Figure가 작아지지 않게 하고 Figure와 설명문의 비율을
  맞춘다.
- 본문이 비어 보이지 않게 하되 긴 문단을 그대로 넣지 않는다. 불릿은 2~4줄, 나머지는
  다이어그램·코드가 말하게 한다. 큰 Figure나 수식이 주인공인 페이지는 불릿 수를 억지로 채우지 않는다.
- 제목 위치·페이지 번호·여백·글꼴 크기는 모든 슬라이드에서 일관되게 유지한다.
- 슬라이드 하단에 원본 자료의 페이지·Figure 번호·출처를 작게 표시한다.

## 3. 글꼴과 크기

크기 표는 [design.md](design.md)에 있다. 그 위에서 지킬 하한선:

- 다이어그램 라벨·표 글자는 **10pt 아래로 내리지 않는다.** 표가 10pt로 안 들어가면 표를 여러
  슬라이드로 나누거나 핵심 행·열만 남긴다.
- 수식은 발표 화면에서 바로 읽히게 **20pt 이상**으로 넣는다. 기호가 작아 안 보이면 수식 설명이
  통째로 무의미해진다.
- 발표자가 설명해야 하는 Figure의 축·범례·주요 숫자는 화면에서 읽을 수 있어야 한다.
- 작은 글씨로 내용을 더 밀어 넣지 말고, 슬라이드를 나눈다.

## 4. 언어

- 슬라이드와 대본은 설정한 언어를 따른다. 기본은 **슬라이드 영어, 대본 한국어**다.
- 영어 슬라이드는 짧은 명사구·질문문으로 쓴다. 문장을 길게 늘이지 않는다.
  전환 슬라이드도 영어 질문으로: `What happens when two pods share one IP?`
- design.md의 말투 규칙(평어체 단정문, 해요체 전환 멘트, 청유형 마무리)은 **한국어로 쓰는 쪽**에
  적용한다. 슬라이드가 영어면 대본에만 적용된다.
- Figure 안의 원문 표기와 고유 용어는 원래 언어를 유지한다. 기술 용어(pod, iptables, TTL)는
  번역하지 않는다.
- 영어 전문용어가 대본에 처음 등장하면 한국어로 뜻을 한 번 풀어준다.
- 같은 개념을 여러 표현으로 바꾸지 않는다. 덱과 대본 전체에서 용어를 하나로 고정한다.

## 5. 발표 대본

발표자는 기본적으로 **이 분야를 처음 접한다고 가정한다.** 대본은 슬라이드 요약이 아니라, 읽으면
개념·문제·방법·결과가 이해되고 그대로 말할 수 있는 완성 원고다. 슬라이드 문장을 그대로 읽는
형태로 쓰지 않는다.

작성 규칙과 슬라이드별 템플릿, 수식·Algorithm 설명 레시피는
[references/script-template.md](references/script-template.md)에 있다. 대본을 쓰기 전에 읽는다.

분량은 발표 시간에 맞춘다. 한국어 발표는 분당 300~330자 정도다. 10분이면 대본 본문 총합이
3,000~3,300자 근처가 되게 하고, 중요한 Figure·수식·Algorithm 슬라이드에 분량을 더 주고 전환·요약
슬라이드는 짧게 쓴다.

## 6. Figure와 시각자료 처리

- 원본 자료의 Figure·Chart·Table·Diagram을 우선 쓴다. 축·범례·단위·캡션이 잘리지 않게 crop을 최소화한다.
- 시각자료만 넣지 않는다. 슬라이드 안에 **"이 자료에서 무엇을 봐야 하는지"** 를 한 줄 적는다.
- 원본 시각자료가 복잡하면 위에 덧칠하지 말고 옆에 번호와 짧은 설명을 배치한다. 필요하면 의미와
  수치를 유지한 채 설명용 도식으로 다시 그려도 된다.
- 다시 그린 도식에는 `adapted from ...` / `simplified view` 표시를 단다. 새로 만든 그림이 원본에
  실제로 있는 결과처럼 보이면 안 된다.
- 시각자료가 없는 내용은 긴 글로 채우지 말고 관계·순서·비교를 보여주는 간단한 도식으로 만든다.
  akbun 그림 언어(design.md)를 쓴다.
- 외부 시각자료를 가져오면 원저자·기관·공식 문서를 우선하고, 슬라이드 하단과 대본 양쪽에 출처를 남긴다.
- **Figure·로고를 어떻게 확보할지는 정해두지 않는다.** PDF에서 잘라내든, 다시 그리든, 도형+라벨로
  대체하든 그 시점에 쓸 수 있는 도구 중 가장 나은 방법을 고른다. 어떤 방법을 썼는지만 밝힌다.

## 7. 내용 정확성

- 원본 자료의 핵심 주장·조건·수치·결론을 정확히 유지한다. **자료에 없는 수치나 인과관계를 만들지 않는다.**
- 원본 자료가 없이 주제만 받은 경우, 확인되지 않은 수치를 사실처럼 쓰지 않는다. 예시가 필요하면
  "시나리오: pod 1개가 분당 1,000 요청 처리" 처럼 **가정임을 드러내는 시나리오 형식**으로 쓴다.
- 성능·수치를 제시할 때는 비교 대상·조건·단위·기준을 함께 쓴다. 특정 조건에서만 성립하는 결과를
  일반 결론처럼 쓰지 않는다.
- 원본의 한계·적용 조건·반례가 있으면 함께 넣는다.
- 제작자의 해석이나 추가 설명은 원본 주장과 구분되게 표시한다. 외부 자료를 더할 때도 원본과 구분한다.
- 불확실하거나 해석이 갈리는 부분은 임의로 확정하지 말고 대본에 주의점으로 적는다.

## 8. 최종 검수

pptx를 실제로 렌더링해서(`references/pptxgenjs-kit.md`의 `macOS에서 QA` 참고) 확인한다. 문제가
있으면 최종 파일을 전달하기 전에 고치고 다시 확인한다.

- Figure·Chart의 축·범례·단위가 잘리지 않았는가? 이미지가 흐리거나 비율이 깨지지 않았는가?
- 수식이 슬라이드에서 읽히는 크기인가? 표 안 글자가 10pt 아래로 내려가지 않았는가?
- 제목·본문·Figure·페이지 번호가 겹치지 않는가? 텍스트가 잘리지 않았는가?
- 헤더 형식(`N. 섹션명`)·위치가 통일됐는가? 페이지 번호가 표지를 제외한 전 슬라이드에 있는가?
- 대본의 슬라이드 번호가 pptx와 일치하는가? 모든 슬라이드에 대본과 출처가 있는가?
- 원본 자료의 핵심 Figure·수식·Algorithm·결과·사례가 빠지지 않았는가? 수치가 원본과 일치하는가?
- 비슷한 내용이 여러 슬라이드에서 불필요하게 반복되지 않는가?
- 대본 글자 수가 발표 시간 안에 들어가는가?
- pptx와 md 파일이 실제로 정상적으로 열리는가?

## 9. 최종 결과물

파일 두 개를 만들고, 최종 답변에는 아래만 간단히 쓴다. 과정 설명·구현 로그는 넣지 않는다.

- 완성된 파일 경로 (`.pptx`, 대본 `.md`)
- 전체 슬라이드 수
- 예상 발표 시간 (대본 글자 수 기준)
- 원본 자료에서 가져온 주요 Figure·표 (원본이 있을 때만)
- 최종 검수 완료 여부

## Google Slides로 가져가기

1. 생성한 .pptx를 Google Drive에 올린다.
2. 더블클릭 → "Google Slides로 열기"를 누르면 레이아웃이 유지된 채 변환된다.
3. Google Slides에는 나눔바른고딕이 없어 다른 고딕으로 대체된다. 글꼴이 중요하면 pptx를
   PowerPoint에서 그대로 쓰고, Google Slides는 공유·협업용으로만 쓴다.

## 예시 (gold reference)

입력 예:

```text
Redis 캐시 스탬피드 발표자료 만들어줘. 15분, 사내 백엔드 스터디용.
```

설정 요약: 15분 / 20장 / 슬라이드당 평균 45초 / 청중 배경지식 부족한 소프트웨어 엔지니어 /
슬라이드 영어 · 대본 한국어 / 라이트 샌드위치.

아웃라인(발췌):

| # | 유형 | 배경 | 슬라이드 제목 | 핵심 메시지 |
|---|---|---|---|---|
| 1 | 표지 | 다크 | **Cache Stampede** and How We Survived It | 핵심 키워드만 노랑 |
| 2 | 목차 | 라이트 | Agenda | 1. What is a cache stampede? … 5. Wrap-up |
| 3 | 실습자료 | 라이트 | Try It Yourself | 예제 repo 링크 + 실습 환경 |
| 4 | 섹션 표지 | 다크 | 1. What Is a Cache Stampede? | 노란 세로 바 |
| 5 | 내용 | 라이트 | Normal Cache Read Path | ①②③ 다이어그램 + 코드 패널(왼쪽) |
| 6 | 전환 | 라이트 | What if 10,000 keys expire at once? | 중앙 3줄 질문 |
| 7 | 내용 | 라이트 | All Misses Land on the Database | 같은 다이어그램 + 빨간 점선·빨간 X |
| … | | | | |
| N | 참고자료 | 라이트 | References | 번호 목록 링크 |

같은 캐시 다이어그램이 5·7·해결책 슬라이드에서 반복되고 마커와 강조만 바뀐다. 제목 열만 세로로
읽으면 "정상 경로 → 동시 만료 질문 → DB 폭주 → 해결"이라는 흐름이 그대로 보인다.
