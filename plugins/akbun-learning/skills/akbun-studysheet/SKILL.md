# akbun HTML 퀵스타트 학습지 만들기

## 목표

입력 자료를 그대로 옮기지 말고, 처음 접하는 사람이 짧은 시간 안에 개념을 이해하고 직접 확인하는 학습 경험으로 재설계한다. 다음 두 학습 성과는 고정하고, 이를 달성하는 서사와 형식은 주제에 맞게 결정한다.

- 학습자가 핵심 개념을 자기 말로 설명할 수 있음
- 학습자가 최소 하나의 검증 가능한 핸즈온을 끝까지 수행할 수 있음

특정 교육 순서나 페이지 종류를 강제하지 않는다. 문제 상황, 원리, 아키텍처, 퀴즈, 트레이드오프, 결론은 필요할 때 선택하는 수단이지 필수 목차가 아니다.

## 작업 흐름

### 1. 범위와 학습 성과 구체화

- 입력에서 이번 퀵스타트가 다룰 핵심 개념과 완주 지점을 한 문장씩 정한다.
- 대상은 해당 개념을 처음 접하는 사람으로 둔다. 꼭 필요한 선행지식만 적시에 설명한다.
- 한 학습지에 여러 독립 주제를 넣지 않는다. 분량보다 이해가 먼저 무너지면 범위를 좁힌다.

### 2. 사실 검증

- 사용자 입력을 정답이 아니라 출발 자료로 취급한다.
- repo 동작은 코드·테스트·실행 결과로, 제품·기술 동작은 공식 문서·명세·원 출처로 확인한다. 바뀔 수 있는 정보는 최신 근거를 조회한다.
- 입력과 근거가 충돌하면 근거에 맞게 바로잡아 작성한다. 잘못된 설명을 학습 내용으로 전달하지 않는다.
- 직접 실행할 수 있는 코드와 명령은 실행해 검증한다. 검증하지 못한 내용은 사실처럼 단정하지 말고 `확인 필요` 또는 `미검증`으로 표시한다.
- 학습 판단에 영향을 준 핵심 출처는 링크 또는 짧은 출처 목록으로 남긴다.

### 3. 학습 경로 설계

- 개념 의존성, 학습자의 첫 성공 경험, 실습 환경을 먼저 파악한 뒤 페이지 순서를 정한다.
- 설명 방식은 주제에 맞게 선택한다. 예: 먼저 실행하고 원리 해석, 개념 지도에서 세부로 이동, 장애 진단, 작은 시스템 조립, 선택지 비교.
- 첫 페이지의 제목·부제·도입 방식·구성을 AI가 결정한다. 고정 문구나 `문제 상황 → 어떻게 풀까?` 구도를 재사용하지 않는다.
- 두 학습 성과를 확인할 장치를 둔다. 형식은 teach-back, 예측, 퀴즈, 디버깅, 결과 비교 등에서 자유롭게 선택한다.
- 한 페이지에는 하나의 인지적 초점만 둔다. 설명을 억지로 같은 형식에 맞추지 않는다.

### 4. 시각화 설계

시각화 개수를 정하지 말고, 글만으로 관계를 파악하기 어려운 지점에 사용한다. 장식용 시각화는 만들지 않는다.

- 구성요소와 경계: architecture/component diagram
- 요청 순서와 시간 흐름: sequence diagram 또는 단계 애니메이션
- 상태 변화: state diagram 또는 전이 애니메이션
- 계층·공간·깊이: 2D 또는 CSS 3D
- 알고리즘·데이터 변화: inline SVG 또는 Canvas 애니메이션

연속된 과정을 설명할 때는 같은 구도를 유지하고 강조만 바꿔 인지 부하를 줄인다. 서로 다른 개념에는 더 적합한 구도를 새로 선택한다. 애니메이션과 3D는 움직임이나 깊이가 이해에 실제로 기여할 때만 사용하고 `prefers-reduced-motion` 대안을 제공한다.

HTML 안의 CSS, inline SVG, Canvas, JavaScript를 우선 사용한다. 외부 라이브러리는 학습 효과에 필수이고 간단한 자체 구현으로 대체하기 어려울 때만 사용하며, 네트워크 의존성을 학습지에 밝힌다.

### 5. 핸즈온 설계

- 가장 작은 유용한 성공 경험을 최소 하나 포함한다.
- 준비 → 실행 → 기대 결과 → 검증 방법이 이어지게 작성한다. 필요한 경우 실패 복구와 정리 단계도 포함한다.
- 명령과 코드는 그대로 복사해 실행할 수 있게 작성한다. 기대 결과는 핵심 부분만 보여준다.
- 체크포인트에서 무엇이 관찰되면 성공인지 명확히 적는다.
- 실습 repo가 있으면 `github 링크: URL`을 남긴다.
- 로컬 실행이 어려운 개념은 HTML 안의 조작 가능한 toy simulation으로 검증 경험을 만들 수 있다. 단순 클릭 효과를 핸즈온으로 부르지 않는다.

### 6. HTML 제작

[assets/template.html](assets/template.html)을 복사해 시작하고 [assets/design.md](assets/design.md)의 시각 언어를 적용한다. 필요한 UI 조각은 [assets/components.html](assets/components.html)에서 골라 사용한다.

- 산출물은 CSS·JavaScript·SVG를 포함한 HTML 한 파일만 만든다. 기본 기능은 오프라인에서도 동작하게 한다. 외부 라이브러리를 예외적으로 쓰면 네트워크 없이도 핵심 내용을 읽을 수 있게 하고 결과 파일은 하나만 만든다.
- 기본 내비게이션과 접근성 동작은 유지한다. 시각화에 필요하면 CSS와 JavaScript를 추가하거나 수정한다.
- 학습지 한 장은 `<section class="page">` 하나로 만든다. 16:9에서 스크롤이나 잘림이 생기면 내용을 압축하지 말고 페이지를 재구성한다.
- 첫 페이지는 `.cover`를 쓸 수 있지만 제목과 내부 구성은 자유롭게 바꾼다.
- ASCII art는 쓰지 않는다. 다이어그램은 HTML/CSS, inline SVG, Canvas 중 가장 단순한 적합 수단을 선택한다.
- 기본은 20장 미만이다. 선행 개념이나 과정 단계가 많아 줄이면 이해 또는 실습 재현성이 훼손되는 복잡한 주제만 20~29장으로 만든다.
- 29장에도 맞지 않으면 내용을 빽빽하게 넣지 말고 학습 목표를 나누도록 제안한다.

저장 위치는 `$HOME/Downloads/<주제-slug>/`로 한다. 파일명은 `studysheet-<주제-slug>-v1.html`로 시작하고, 같은 주제를 다시 만들면 v2, v3으로 올려 이전 파일을 덮어쓰지 않는다.

## 글쓰기 원칙

- 초심자가 첫 문장에서 막히지 않는 짧고 자연스러운 한국어로 쓴다.
- 산문, 불릿, 코드, 질문 중 이해에 가장 적합한 형식을 선택한다. 명사형 종결이나 개조식을 모든 페이지에 강제하지 않는다.
- 영어 기술 용어는 억지로 번역하지 말고, 처음 나올 때 맥락으로 뜻을 알 수 있게 한다.
- 과장 표현을 쓰지 않는다. 불확실한 내용은 불확실성을 그대로 드러낸다.
- 일반 상식보다 이 주제에서만 필요한 원리·관찰·판단 기준에 지면을 쓴다.

## 검증

완료 전에 다음을 확인한다.

- 핵심 개념을 자기 말로 설명하게 만드는 확인 장치가 있는가?
- 최소 하나의 핸즈온에 실행 방법, 기대 결과, 성공 판정이 있는가?
- 중요한 사실이 코드·실행 결과·공식 또는 원 출처와 맞는가?
- 제목, 첫 페이지, 학습 순서가 주제에 맞게 결정됐는가?
- 시각화가 관계·흐름·상태·공간 이해에 기여하는가?
- 기본 20장 미만이며, 복잡성 근거가 있을 때만 20~29장인가?
- 외부 라이브러리를 피했고, 사용했다면 이유와 네트워크 의존성을 밝혔는가?
- 브라우저에서 페이지 이동, 키보드, 인터랙션, 전체 화면, reduced motion이 동작하는가?
- 16:9와 좁은 화면에서 내용이 잘리거나 겹치지 않는가?
- 지정 경로와 버전 파일명으로 저장했고 이전 결과물을 보존했는가?
